# S10 - Invocation identity of a host-tool call (`board` today, `sidekick` tomorrow)

Date 2026-10-21. Read-only spike. Versions probed: codex-cli 0.163.0, Claude Code 2.1.302, Hermes agent checkout under `%LOCALAPPDATA%\hermes\hermes-agent`.

## 1. Question

For each adapter (Claude Code, Codex, Hermes, ACP, Prime) which native identifier of ONE tool call reaches the bridge, does it reach `boardRequest` / `coordinatorRequest` and the host, is it stable across a transport retry but new for a model re-issue, and what survives a bridge restart (runner counters `piui-board-N`)? Then: propose the identity tuple and a per-adapter guarantee.

## 2. Method

- Static reading: `crates/piui-runtime/bridge/{runner,claude,codex,codex-pool,acp,hermes,prime}.mjs`, `CONTRACT.md`, `workspace_runtime.rs`, `workspace_api.rs`, `orchestration_scheduler.rs`, `orchestration_api.rs`, `piui-orchestration/src/coordinator.rs`.
- Claude Code: string/code inspection of the installed binary (`claude.exe` is a Bun bundle, the JS is readable with `grep -a`). No model, no run.
- Codex: generated the app-server schema (`codex app-server generate-ts|generate-json-schema --experimental`, in `fusion-spikes/codex-schema*`), then ran the real `codex app-server` against a LOCAL mock Responses endpoint (`fusion-spikes/probe/mock.mjs`, `mock2.mjs`) with a scratch `CODEX_HOME`. No network model, no paid call, user's `~/.codex` untouched. The mock model emits a `function_call` and the probe plays the client, so we see the exact `item/tool/call` frames.
- Hermes: read the Python MCP client (`tools/mcp_tool_handlers.py`).
- Not run: Claude Code itself (would need a model), Prime SDK, Hermes, any ACP agent.

## 3. Findings

### 3.1 What the bridge does today (common to all)

- `runner.mjs:101,104` `let coordinatorSequence = 0; let boardSequence = 0;` are per-process counters. `runner.mjs:135` `piui-coordinator-${++coordinatorSequence}`, `runner.mjs:153` `piui-board-${++boardSequence}`.
- `runner.mjs:137` the coordinator pending slot stores `toolCallId: metadata?.toolCallId` but it is never read again, and `emit({type:"coordinatorRequest", requestId, operation})` (`runner.mjs:~146`) carries no native id. `boardRequest` (`runner.mjs:149-163`) ignores `metadata.toolCallId` entirely (only `metadata.signal` is used).
- Rust: `NativeEvent::BoardRequest { request_id, operation }` (`workspace_runtime.rs:1033`) and `CoordinatorRequest` (`:1026`); the enum is `#[serde(deny_unknown_fields)]` (`:~990`), so any new field needs a Rust change plus a bridge contract bump.
- `workspace_api.rs:3575-3606` BoardRequest -> `hooks.handle(&binding, &turn_key, operation)`. The host never sees `request_id` or any native id for board calls; the only host-side correlation is `turn_key = "{session_id}:{turn counter}"` (`workspace_api.rs:567`), used for the write budget.
- Coordinator path: `orchestration_scheduler.rs:1472` `request_id: format!("{}-{}", origin.session_id, origin.request_id)` -> `orchestration_api.rs:1304` `record_agent_request(...)` -> `coordinator.rs:1126-1148`: same id + same (session, member, operation) = "identical retry, return false"; same id with different authority/input = `AgentRequestConflict` (`coordinator.rs:39`).
- Pending host calls are settled as failures on turn end / interrupt / EOF / dispose (`runner.mjs:~113-118,168,175`), but a request the host already started is NOT undone; a model that sees `board-cancelled` may re-issue it.

### 3.2 Claude Code (MCP JSON-RPC over the session HTTP server)

- Server: `claude.mjs:1269-1340` (`handleMcp`). Only `message.id` is read; the call is passed as `toolCallId: \`mcp-${String(message.id)}\`` (`claude.mjs:1325` board, `:1334` workspace), and the runner drops it.
- JSON-RPC `id` is a per-MCP-client counter shared with `initialize`/`tools/list`/`ping` (standard MCP SDK behaviour; Codex's rmcp client shows the same 0,1,2 sequence in `probe/out2/mcp.log`). Claude Code restarts re-create the client: `restartWithSettings` relaunches the process on the same session (`claude.mjs:1438-1443`) while the HTTP server and bearer token persist (`mcpToken` is created once, `:1275`). So `mcp-N` is NOT unique per call over the life of a session: it restarts from low numbers after every relaunch/reconnect. Unverified by a live run, but follows from the client design.
- The stable native id exists but is not read. Binary 2.1.302, the MCP call wrapper builds the request `_meta` as `{...ITn(config, mcpRequestMeta), ...(toolUseId && {"claudecode/toolUseId": toolUseId}), ...}` where `toolUseId = ee.toolUseId ?? as(ue)`, i.e. the `toolu_...` id of the model's `tool_use` block. Sub-agent attribution keys `claudecode/agentId` / `claudecode/agentType` exist in the same meta builder (`QTn`), presence per call unverified.
- Retry behaviour (binary): a call is re-dispatched in a `for(;;){... continue}` loop with the SAME `toolUseId` and a freshly allocated JSON-RPC id after (a) MCP "session recovery" (`Retrying tool '...' after session recovery`, one retry), (b) auth reconnect (`isAuthRetry`), (c) elicitation completion. Our server issues no `Mcp-Session-Id` and returns static 403 (not 401) so (a) and (b) are unlikely in practice, but the invariant is: transport retry = same `claudecode/toolUseId`, new JSON-RPC id; model re-issue = new `toolu_` id. Same-JSON-RPC-id replay: not seen in the code paths read (unverified for the HTTP transport internals).
- `handleMcp` never listens for request abort: if Claude gives up on a call (`transport dropped mid-call`, user interrupt) the host side effect is still executed.

### 3.3 Codex (dynamic tool `item/tool/call`)

Schema (`fusion-spikes/codex-schema/DynamicToolCallParams.json`): required `arguments, callId, threadId, tool, turnId`, optional `namespace`.

Observed frame (probe `A TOOLCALL`, the model emitted `call_id: "call_native_1"`):
`{"method":"item/tool/call","id":0,"params":{"threadId":"01a15eb9-...","turnId":"01a15eb9-0204-...","callId":"call_native_1","namespace":"piui","tool":"sidekick","arguments":{"q":"hello"}}}`

- `callId` is exactly the model's Responses `call_id` (round-trips into `function_call_output.call_id` in the next model request, `probe/out/req-02.json`).
- `turnId` is a UUIDv7 unique per turn, survives app-server restarts (persisted thread). `threadId` = native thread id (the PiUI native binding).
- The JSON-RPC server-request `id` is a per-app-server-process counter: it was `0` in the first process and `0` again after a restart (phase C). Shared counter across threads inside one process (also in `codex-pool.mjs`, where all pooled threads share it; `route()` forwards the frame unchanged, `codex-pool.mjs:~32-45`).
- The bridge validates `params.threadId === nativeId`, string `turnId`/`callId` (`codex.mjs:849-860`), keys pending calls `board:${message.id}:${callId}` and passes `toolCallId: params.callId` (`codex.mjs:869`), again dropped by the runner.
- Transport retry vs new model call: a re-sampled model response gets a new `call_id` (provider-assigned). A replay of the same `function_call` item (stream resume) would keep the same `call_id`; this was not reproducible with the mock (unverified).
- After the bridge (and the app-server child) restarts and the thread is resumed, a new call arrives with a fresh `turnId` and `id: 0` again (probe phase C, `callId` reused by my mock on purpose - the tuple `(threadId, turnId, callId)` stays distinct).
- If sidekick were attached through a per-thread MCP server instead (see S7), `tools/call` `_meta` carries `callId`, `threadId`, `sessionId`, `itemId` (`fc_<uuid>`), `x-codex-turn-metadata.turn_id`, `progressToken` (`probe/out2/mcp.log`): equivalent identity, JSON-RPC id again a per-connection counter.

### 3.4 Hermes and ACP (loopback HTTP MCP)

- `acp.mjs:473-501` and `hermes.mjs:~116-150`: the bridge calls `boardRequest(message.params.arguments, {})` / `coordinatorRequest(..., {})` (hermes passes no metadata at all for workspace). No JSON-RPC id, no `_meta`, no signal.
- Hermes' MCP client calls `server.session.call_tool(tool_name, arguments=args)` with no `meta` (`tools/mcp_tool_handlers.py:292`), so nothing native is on the wire except the JSON-RPC id. It retries once after auth recovery / session-expired reconnect / dead stdio child (`mcp_tool_handlers.py:126-217`): same arguments, new JSON-RPC id. Our server is stateless HTTP (no session id), so these paths are unlikely for `piui-workspace`, but the guarantee must not rely on their absence.
- ACP agents emit `session/update` `tool_call` with their own `toolCallId` (`acp.mjs:238`), but it is not correlated with the MCP `tools/call` (different channel, no shared key). Other ACP agents' MCP clients: unverified.
- Note `hermes.mjs` also answers non-tools methods with 400 when `message.id` is absent (falls to `throw fail('unknown-method')`), harmless here.

### 3.5 Prime (SDK custom tool)

- `prime.mjs:101,140`: `async execute(toolCallId, operation, signal)` and `boardRequest(operation, { toolCallId, signal })`. `toolCallId` is the SDK-provided id of the model tool call (also used for the timeline block, `prime.mjs:392-393`). It is the only adapter where the id and an abort signal both arrive naturally.
- Uniqueness per provider (synthetic ids for providers that do not issue ids, replay after session reload): unverified.

### 3.6 Bridge restart

- `boardSequence`/`coordinatorSequence` restart at 1, `boardPending`/`coordinatorPending` are lost, the HTTP MCP token is regenerated (Claude) and the app-server child is killed (Codex). So no native retry can cross a bridge restart; every call after it is a genuine new call.
- Latent defect in the existing coordinator dedup: the durable request key is `{session_id}-piui-coordinator-N` (`orchestration_scheduler.rs:1472`) and `N` restarts from 1 after a bridge restart of a still-live PiUI session. If the same session ever resumes inside the same run (managed Claude/Prime/Hermes resume is possible; Codex managed resume is refused, `codex.mjs:47`), the new call #1 is treated as "identical retry" and silently returns the old outcome when input is the same (lost send / spawn), or fails with `AgentRequestConflict` when it differs. Whether the scheduler resumes managed sessions in-run is unverified; fixing needs only an epoch in the id.
- The board path has no such issue only because the host does not use `request_id` for anything but the single pending reply.

## 4. Conclusion and proposal

No adapter exposes a retry-proof id by default; today nothing native reaches the host. A single identity must therefore be assembled from three layers and the guarantee differs per adapter.

### 4.1 Tuple the bridge should add (`boardRequest`, `coordinatorRequest`, future `sidekickRequest`)

```
identity = {
  epoch:   <random UUID created once per runner process (createRunner)>,   // runtime epoch
  seq:     <the existing counter>,                                        // requestId = `piui-<tool>-<epoch8>-<seq>`
  callRef: <hex(sha256(harness | scope | nativeCallId))[0..32]> | absent, // never the raw native id (CONTRACT: native ids stay adapter-private)
  opHash:  <hex(sha256(canonicalJson(validatedOperation)))[0..32]>        // key-sorted canonical form after validateBoardOperation
}
```

`scope` / `nativeCallId` per adapter: Claude `""` / `_meta["claudecode/toolUseId"]` (fallback absent, never `mcp-<jsonrpcId>`); Codex `threadId+turnId` / `callId`; Prime `sessionId` / `toolCallId`; Hermes and ACP: absent. The origin session stays host-derived from the runtime binding (as today), so the host key is `(sessionId, callRef)`. Carrying it needs `NativeEvent::{Board,Coordinator}Request` to gain an optional `identity` object (deny_unknown_fields -> Rust change, bridge contract/CONTRACT.md update, compatibility test).

Minimal, no-Rust variant: only prefix the epoch into `requestId` (`piui-board-<epoch8>-<seq>`); this alone fixes the coordinator restart collision and makes `boardResponse` immune to cross-restart stale ids.

### 4.2 Host rules

1. `callRef` present: key `(sessionId, callRef)`; first admission stores `opHash` and the outcome; same `callRef` + same `opHash` = replay, return the stored outcome without re-executing; same `callRef` + different `opHash` = `IDENTITY_CONFLICT` refusal (mirrors `coordinator.rs:1129-1148`). Persist durably next to the sidekick/session record; do not key on `epoch`.
2. Always also keep a semantic guard `(sessionId, turn_key, opHash)`: a model re-issue (new id, same operation) within one turn returns the existing outcome flagged as duplicate instead of starting a second sidekick. This is the only protection for Hermes/ACP and the only one against "result lost -> model retries".
3. `epoch` + `seq` identify the pending reply (`stale-*` on mismatch) and diagnostics; they are never the dedup key.
4. Do not start side effects before checking rule 1; add request-abort handling (`request.on('close')` -> `AbortSignal`) in Claude/ACP/Hermes servers so an abandoned call is cancelled before the host acts, and make sidekick start effects commit before the reply is sent (idempotent on replay).

### 4.3 Per-adapter guarantee

| Adapter | Native id used | Transport retry | Model re-issue | Bridge restart |
|---|---|---|---|---|
| Claude Code (2.1.302) | `_meta["claudecode/toolUseId"]` (verified in binary; undocumented, version-dependent) | same callRef -> exactly-once | new toolu id -> only the semantic guard | new epoch, no cross-restart retry; ids unique |
| Codex dynamic tool | `callId` + `turnId` + `threadId` (verified) | same callRef -> exactly-once | new call_id -> semantic guard | app-server dies with it; thread resumes with new turnId |
| Prime | SDK `toolCallId` (read from code; provider uniqueness unverified) | exactly-once if ids unique per session | semantic guard | new epoch |
| Hermes | none | not distinguishable | not distinguishable | new epoch |
| ACP | none (agent `toolCallId` is on another channel) | not distinguishable | not distinguishable | new epoch |

For Hermes/ACP the honest guarantee is "at-least-once with same-turn duplicate suppression by operation hash", not exactly-once. If a missing `_meta["claudecode/toolUseId"]` is seen (older Claude Code), degrade Claude to that same weaker class.
