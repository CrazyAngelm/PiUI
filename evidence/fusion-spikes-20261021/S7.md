# S7 - Can a RESUMED Codex lead get the `sidekick` tool?

Date 2026-10-21. Read-only spike on codex-cli 0.163.0 (Windows). No repo file changed, no paid model, user `~/.codex` untouched.

## 1. Question

Does `thread/resume` accept dynamic tools (or an equivalent) in this Codex version? Can per-thread MCP servers be attached on resume / via config overrides without touching the user's global config, and is that safe with the shared app-server pool (`codex-pool.mjs`)? What does the bridge do today (`unsupported-board-tool-resume`)? Is there a safe way for a resumed Codex thread to get `sidekick`, or must Fusion hand off to a new chat?

## 2. Method

- Generated the protocol: `codex app-server generate-ts --experimental` and `generate-json-schema --experimental` into `fusion-spikes/codex-schema-ts` and `fusion-spikes/codex-schema` (read-only generation).
- Read `codex.mjs`, `codex-pool.mjs`, `CONTRACT.md`, `workspace_runtime.rs`, `docs/BOARD.md`.
- Ran the REAL `codex app-server` (stdio JSON-RPC, `experimentalApi: true`) with `CODEX_HOME` pointing into the scratchpad and a `config.toml` that routes the model to a local mock Responses server (`wire_api = "responses"`, `127.0.0.1`). The mock records every `/v1/responses` request body (so the exact tool list the model would see) and can emit a `function_call`. A second tiny local MCP server (streamable HTTP) played the sidekick. Scripts: `fusion-spikes/probe/mock.mjs` (dynamic tools: start, resume in new process, tool call after resume, fork) and `mock2.mjs`/`mock3.mjs` (per-thread MCP on resume). Each phase uses a NEW app-server process so the thread is rebuilt from its rollout, i.e. the same situation as PiUI resuming after an app restart.

## 3. Findings

### 3.1 Protocol: `thread/resume` has no `dynamicTools`

`codex-schema-ts/v2/ThreadStartParams.ts` (the only place the field exists; `grep -rl dynamicTools` hits only `ThreadStartParams`, `DynamicToolSpec`, `ClientRequest.json`, the v2 schema bundles):

```ts
environments?: Array<TurnEnvironmentParams> | null, dynamicTools?: Array<DynamicToolSpec> | null,
selectedCapabilityRoots?: Array<SelectedCapabilityRoot> | null,
```

`ThreadResumeParams.ts` (and `ThreadForkParams.ts`, `TurnStartParams.ts`, `ThreadSettingsUpdateParams.ts`) have no tool list; resume has `model, modelProvider, serviceTier, cwd, runtimeWorkspaceRoots, approvalPolicy, approvalsReviewer, sandbox, permissions, config, baseInstructions, developerInstructions, personality, excludeTurns, initialTurnsPage` (+ unstable `history`, `path`). Empirical: sending an extra `dynamicTools: [{namespace piui, tool late}]` on `thread/resume` is accepted and silently ignored: the model request tools list shows no `piui` namespace (`probe/out2/req-02.json`). So the repo's earlier conclusion (docs/MULTI_HARNESS_IMPLEMENTATION.md:88, CONTRACT.md:75 "on `thread/start` only") is right about the parameter.

### 3.2 But dynamic tools are PERSISTED with the thread and come back on resume

New finding that changes the picture. A thread started with `dynamicTools` writes them to the rollout `session_meta`:

```
session_meta keys: session_id, id, timestamp, cwd, runtime_workspace_roots, originator, cli_version, source, model_provider, base_instructions, dynamic_tools, history_mode, context_window
dynamic_tools = [{"type":"namespace","name":"piui","description":"probe","tools":[{"type":"function","name":"sidekick",...}]}]
```
(the binary also contains a `thread_dynamic_tools` table in `state_5.sqlite`: columns `thread_id, position, name, description, input_schema, defer_loading, namespace`.)

Experiment (`mock.mjs`, new `codex app-server` process per phase):

| Phase | Action | Model request tools list |
|---|---|---|
| A | `thread/start` + `dynamicTools` (piui.sidekick), turn, model calls the tool | `piui: [sidekick]` present (req-01, req-02) |
| B | NEW process, `thread/resume {threadId}` (no tools param), plain turn | `piui: [sidekick]` STILL present (req-03) |
| C | NEW process, resume, model issues `piui.sidekick` | client receives `item/tool/call {threadId, turnId(new), callId, namespace:"piui", tool:"sidekick"}` with JSON-RPC `id: 0` again |
| F | NEW process, `thread/fork {threadId}`, turn | fork also lists `piui: [sidekick]` (`probe/out5/req-03.json`) |

So: a thread that was STARTED with `piui.sidekick` keeps it across resume and fork, and its calls are delivered to whichever client resumed it. Conversely nothing can ADD a dynamic tool to a thread that was started without it (no param on resume/fork/turn/settings), and the tool's schema is frozen at thread creation.

### 3.3 What the bridge does today

- `codex.mjs:54-60`: `boardEnabled = boardRequested && typeof boardRequest === "function" && !config.nativeId`; on resume it emits `{type:"notice", code:"unsupported-board-tool-resume"}` and does not register anything.
- `codex.mjs:1310-1336`: `dynamicTools` only added to `thread/start` (`{ ...startThreadParams, ephemeral:false, dynamicTools }`); `thread/resume` gets `threadParams` without it (the bridge already passes a `config` object there, e.g. `mcp_servers.<id>.enabled` rules, `codex.mjs:1318-1321`).
- `codex.mjs:47-49`: managed coordinator + resume is refused (`unsupported-coordinator-resume`), `codex.mjs:44-46` requires the callback.
- Host: `HarnessKind::supports_board_tool(resumed)` returns `!resumed` for Codex (`workspace_runtime.rs:245-252`); `NativeNoticeCode::UnsupportedBoardToolResume` (`:978`); docs/BOARD.md:163.
- Consequence discovered here (existing defect, not caused by this spike): a Codex thread STARTED with `piui.board` (any 0.2.x chat with the board enabled) still shows the `board` tool to the model after a resume, because of 3.2, but the bridge now treats it as disabled: `handleNotification` routes `namespace piui / tool board` to `answerBoardCall` (`codex.mjs:900-902`) which fails the `!boardEnabled` guard (`:852`) and answers `invalid-board-call`. The notice also tells the user the tool is unavailable while it is actually advertised. Any other `item/tool/call` goes to `answerCoordinatorCall`, which answers `invalid-coordinator-call` (`:803-822`).

### 3.4 Per-thread MCP via `thread/resume` `config` (no global config change)

`ThreadResumeParams.config: { [key]: JsonValue }` accepts dotted-key and object overrides. Experiment (`mock2.mjs`, scratch `CODEX_HOME`, thread T1 created WITHOUT tools, then NEW process):

```
thread/resume { threadId: T1, excludeTurns: true,
  config: { "mcp_servers.side": { url: "http://127.0.0.1:18767/mcp",
            bearer_token_env_var: "SIDE_TOKEN",        // or http_headers: {Authorization:"Bearer lit-1"}
            default_tools_approval_mode: "approve" } } }
```

Results:
- The model request for T1 lists a new namespace `mcp__side: [sidekick]` (`probe/out2/req-02.json`). The tool is invoked as `{name:"sidekick", namespace:"mcp__side"}` (a `mcp__side__` suffix is wrong: "unsupported call").
- A SECOND thread T2 started in the SAME app-server process has no `mcp__side` namespace (`req-04.json`): the attachment is thread-scoped, not process- or user-global. `CODEX_HOME/config.toml` was byte-identical afterwards. Relevant for `codex-pool.mjs` (one shared app-server for all pooled sessions): per-thread `config` does not leak between pooled threads (verified on one process, two threads).
- Without `default_tools_approval_mode: "approve"` the first call raises a server request `mcpServer/elicitation/request` (`codex_approval_kind: mcp_tool_call`, "Allow the side MCP server to run tool ..."), i.e. a user approval prompt; with it the call went straight through (`tools/call` logged, no elicitation).
- Auth: both `bearer_token_env_var` (needs the env var in the app-server process env; in the SHARED pool the env is fixed at spawn, so per-session secrets don't fit) and literal `http_headers` work (`probe/out3/mcp.log` shows `Authorization: Bearer lit-1`). The literal travels in the JSON-RPC `config` param, not argv.
- Identity delivered to the MCP server: `tools/call params._meta = {callId, threadId, sessionId, windowId, itemId (fc_<uuid>), x-codex-turn-metadata{turn_id,...}, progressToken}` (see S10).
- Not tested: attaching on a thread that is currently RUNNING in the app-server (schema doc: "If thread_id identifies a running thread, app-server rejoins that thread"; config likely ignored); `thread/fork` + `config`; whether the attachment persists to the rollout (it did not appear in `session_meta` keys, so assume it must be re-sent on every resume, which the bridge does anyway).

### 3.5 Rejected alternatives

- `config/value/write`, `config/batchWrite`, `skills/config/write`: write the user's Codex config - forbidden by AGENTS.md ("never modify the user's global auth/config").
- `thread/inject_items`: injects Responses items into model-visible history only; it does not register a callable tool.
- `mcpServer/tool/call` (client request): lets the client call an MCP tool; it does not give the model a tool.
- `codex -c mcp_servers...` at process level: global to the app-server, wrong for a shared pool (and changes the launch contract).

## 4. Conclusion

1. `thread/resume` does NOT accept dynamic tools in 0.163.0 (verified in the generated schema and by an ignored-field probe).
2. There ARE two safe routes for a resumed Codex lead:
   - Route A (free, already persisted): if the thread was started with the host tool in `dynamicTools`, it still has it after resume/fork; the bridge only has to stop refusing it. Fix needed in `codex.mjs`: allow the board/sidekick handler on resume when the thread's persisted `dynamic_tools` contain the namespace (bridge can read `session_meta.dynamic_tools` from the native rollout path read-only, or the host can persist a "started with host tools vX" flag), and answer a clean refusal instead of `invalid-board-call` when the feature is off. Consequence for Fusion: register `piui.sidekick` (additive, permissive schema, versioned by a field) on EVERY fresh Codex `thread/start`, even when Fusion is off for that chat, because the tool list can never be extended afterwards.
   - Route B (older threads that never had it): per-thread loopback MCP server attached through `thread/resume` `config.mcp_servers.<unique-id>` with `default_tools_approval_mode: "approve"` and literal `http_headers` bearer. It is thread-scoped (verified against a second thread in the same app-server), does not touch the user's config, and the model sees it as `mcp__<id>/sidekick` (different tool name from the dynamic `piui/sidekick`, so instructions and the tool name in the timeline differ). It needs a loopback HTTP server inside the Codex adapter (reuse the Claude `handleMcp` pattern), an ADR note because CONTRACT.md says the Codex coordinator uses "no MCP server or global config changes", and conflict handling with the user's own `resourceRules` (`mcp_servers.<id>.enabled`, `codex.mjs:1318`). Do not use this route for a thread that is already running in a pooled app-server (untested).
3. Default for Fusion v1: use Route A for threads created after Fusion ships, show `unsupported-board-tool-resume`-style notice (renamed) for older Codex threads, and offer "continue in a new/forked chat" (a fork of an old thread does NOT gain the tool because `thread/fork` has no `dynamicTools`; it inherits the parent's). Route B is a viable opt-in follow-up, not required for a safe v1.

## 5. Open items (unverified)

- Real provider/auth path (ChatGPT) was not used; the mock proves what the app-server sends, not what a real backend does with the namespaced tool (same Responses `tools` array, so expected identical).
- Persistence of `dynamic_tools` for threads created by older Codex versions (0.147 notes say "no dynamicTools parameter on resume"); the persisted-tools behaviour was observed only on 0.163.0, and the PiUI-verified version range is in `native_version.rs` (re-verify at each bump; `codex.mjs` already gates versions).
- Whether rollouts created before a thread materialises (no first turn yet) keep `dynamic_tools`: observed `session_meta` has them once a turn/inject creates the rollout; an unmaterialised thread cannot be resumed at all (`no rollout found`).
- `thread_dynamic_tools` SQLite table content: empty in the probe before any turn; its role versus rollout `session_meta` not established (resume worked from the rollout either way).
- Route B: running-thread rejoin, `thread/fork` + `config`, behaviour when the user already has an MCP server with the same id, Windows loopback firewall prompts, startup timeout of the MCP handshake on the first turn.
- Whether the model-side tool description limits (namespace description, `deferLoading`) change how aggressively the model uses `piui.sidekick`.
