# S11 - Reopen with frozen policy

All paths are relative to `D:\Projects\PIUI\apps\desktop\src-tauri\src\` unless stated otherwise. Static reading only; nothing was run.

## Question

1. Every path that creates or reopens a native session, with the config each one builds and who can trigger it.
2. How managed orchestration runs keep a frozen launch config across an app restart.
3. The minimal design for a broker-owned reopen of a sidekick session: where the frozen membership record lives, which WebView commands must reject a sidekick session id, and how board and plugin-MCP injection are suppressed.

The single funnel is `spawn_pending` (`workspace_api.rs:1517`) -> `spawn_native` (1105) -> `NativeRuntime::spawn`. Almost every path reaches it via `RuntimeStartOptions` (740-752). The exceptions are the two probe paths in rows 5 and 6.

Both the create and reopen paths take the same two injections inside `spawn_pending` (`workspace_api.rs:1517`):

- **Plugin MCP.** `plugin_mcp_servers` (1080-1103) returns servers unless `managed || record.run_id.is_some() || !harness.accepts_session_mcp()`. `managed` is computed at 1538-1542 from `coordinator`, `allowed_tools`, or non-empty `resource_rules`. For rows 1-3 it is false, so the provider is called (the provider is installed at `lib.rs:884-893`).
- **Board.** Lines 1544-1554 call `board_setup` for every record whose `resume_binding` resolves (`resume_binding` is `workspace_api.rs:2424-2437`). `board_setup` (1048-1070) builds a `BoardBinding` from the record, and `board_sessions::setup_for` (`board_sessions.rs:36-66`) returns `HostTool::Board` plus an instruction block. The only gates are `board.enabled` and `harness.supports_board_tool(resumed)`. Nothing in `board_setup` consults permission, a run flag, or any "role". The returned `host_tools` and merged instructions go straight into `NativeRuntimeConfig` (1588) and into `LiveState.board` (1700-1710). So **run members also receive the board tool**: `setup_for` uses `run_id` only to decide whether to attach the instruction block, and `agent_identity` (`board_sessions.rs:99-135`) gives them teammate permissions or read+comment.

Consequence: the reviewer's concern is confirmed. A sidekick created via row 1 or 3 or reopened via row 2 would silently pick up instructions=None, allowed_tools=None, native_subagents=None, the board tool, plugin MCP, and (for Claude) the user's global MCP servers. The latter is because `--strict-mcp-config` is added only together with a tool allowlist (`claude.mjs:1412`).

## 2. How managed runs keep config across restart: they do not reopen

There is **no precedent for a frozen-config reopen**. The scheduler never reopens a run member after a restart.

- **Frozen source of truth.** The frozen config is not stored on the session record. `PersistedSession` (`workspace_store.rs:19-50`) keeps only `profile_id`, `run_id`, `member_id`, `permission_mode`, and the native binding. The config is re-derived at launch time from the durable run snapshot: `Run.definition` holds the profiles, team and pipeline. `profile_for_step` (`orchestration_scheduler.rs:2140`) and `launch_policy(profile, offline_caps)` (`harness_configuration.rs:117-269`) rebuild everything. A defense-in-depth check asserts the lease profile equals the snapshot profile (`orchestration_scheduler.rs:588`). The spawn path re-validates the same way (1524-1532, 1614).
- **Restart behavior.**
  - `OrchestrationApiState::open` calls `store.recover_interrupted_runs()` (`orchestration_api.rs:299`).
  - That calls `Coordinator::restore` (`crates/piui-orchestration/src/coordinator.rs:981-1003`), which turns Running tasks into `Uncertain` with `lease_id = None`.
  - They are never made ready again; unit test `tests.rs:783`, `restored_running_work_becomes_uncertain_and_is_not_replayed`.
  - Only the user can reconcile or retry (`orchestration_reconcile_uncertain_task_v6` and `orchestration_retry_uncertain_task_v6`).
- **Run sessions refuse the ordinary reopen route.** `prepare_open` (`workspace_api.rs:1374-1379`) returns `not_supported` when `record.run_id.is_some()`. The comment says the session cannot be reopened "without their snapshotted coordinator authority", and that Codex cannot restore dynamic tools on `thread/resume`. History stays readable through the process-free path (`Snapshot` command, 3157-3171, `historical_snapshot`).
- **Messages to non-live members.** `deliver_managed_message` (1883) calls `send` (1892), which returns `closed` for a non-live runtime (1898-1900). The scheduler keeps the message `Accepted` (`orchestration_scheduler.rs:1739-1755`, 1773-1818); it is flushed only when a new execution starts.
- **Other `run_id` guards (these protect run sessions, not sidekicks):**
  - `workspace_composer.rs:545` (composer rejects run sessions);
  - `workspace_composer_inputs.rs:373` (the catalog command);
  - `workspace_api.rs:3067` (lifecycle delete);
  - `workspace_api.rs:1086` (no plugin MCP);
  - `pipeline_library.rs:639-641` (`session_is_run` check);
  - `board_sessions.rs:55` (no chat instruction block).
- **Gap in the same guard family.** The `workspace_command_v15` verbs `Send`, `Interrupt`, `SetModel`, `RenameSession` and `Respond` (`workspace_api.rs:3240-3289`), and `workspace_settings_v16` Set (2655-2727), call only `authorize_live_session` (3293-3304). It checks workspace trust, **not** `run_id`. A WebView can therefore already send, change model, or rename into a *live* run-member session. Only the composer and composer-inputs commands refuse. Do not reuse "the run_id guard" as the template; it is incomplete.

Net: for a sidekick, "frozen across restart" has to be built; it cannot be copied from the run path.

## 3. Minimal design: broker-owned sidekick reopen

### 3.1 Where the frozen membership record lives

**Recommendation: a new host-private side table, `SidekickStore` (dir `workspace-sidekick-v1`), keyed by sidekick session id.** It is loaded at `WorkspaceHost::open` into an in-memory map and written by atomic generation files, like `WorkspaceRegistry` (`workspace_store.rs:81-118`).

- **Not `PersistedSession`.** The struct is `deny_unknown_fields` (`workspace_store.rs:18`) and registry `version: 1` (`workspace_store.rs:12`). A new field makes a new-to-old downgrade skip the newest generation. The per-session side-table precedent is `SessionTools` / `SessionPlacement` (`session_placement.rs:20-21,28-90`, used via `self.inner.tools.placement()`, `workspace_api.rs:1016`). Same pattern, but a separate store so the placement version is untouched.
- **Registry row is still needed.** A sidekick still needs a `PersistedSession` row, because `update_binding_and_metadata` (2373) and `resume_binding` (2424) depend on `native_id` and `native_path`. The row has `run_id = None`, `profile_id = None`.
- **Record fields:**
  - `sidekickSessionId`, `leadSessionId`, `workspaceId`;
  - `harness`, pinned `model` and `thinkingLevel`;
  - frozen `permissionMode`, plus the lead's permission mode at admission (evidence for the same-or-less check);
  - `instructions` (the verbatim appended text, or a versioned template id plus a hash, so a template edit cannot silently change a persisted sidekick);
  - `allowedTools` (Some, explicit), `nativeSubagents=false`, `networkAccess=false`, `hostTools=[]`, `pluginMcp=false`, `resourceRules` (None);
  - `cwd` binding (the project path or the lead's worktree binding);
  - a `policyRevision` / `frozenAt` stamp.

### 3.2 Reopen path

Add `prepare_sidekick_open(&self, sidekick_id)` beside `prepare_open`. It builds `RuntimeStartOptions` **from the store**, not from `ordinary_open`. It sets `instructions`, `allowed_tools=Some`, `native_subagents=Some(false)`, `network_access=false`, `model` and `thinking`, plus a new `RuntimeStartOptions.board: Disabled` and `plugin_mcp: Disabled` (below).

- **Callers.** Only the broker (the `sidekick` host-tool handler) calls it. The WebView never does.
- **Locking.** It uses the same `reserve_start` / `start_outside_gate` machinery (1403-1436, 1477-1500), so the per-session start slot, the cancel-on-trust-revoke behavior (2274) and the concurrent-open dedupe (test `concurrent_opens_of_one_session_share_a_single_native_start`, 5724) all still apply.
- **Admission recheck on every (re)open.** Re-run the same-or-less check against the *current* lead record's permission mode (`PersistedSession.permission_mode` of the lead). Refuse (or reopen at the lesser mode) if the lead has narrowed. This is not a `launch_policy` check (see S8-static for what the monotonic function can and cannot express).
- **Pre-flight on resume.** Refuse to resume if the stored `nativeId` / `nativePath` is missing (Claude already fails closed: `claude.mjs:1380-1382`; the host side is `known_absent_draft`, `workspace_api.rs:2407-2422`, which starts fresh if never materialized). The broker must decide whether a lost transcript means "start a fresh sidekick" or "fail"; silently starting fresh drops the sidekick's context.
- **Harness behavior to rely on.**
  - Claude re-applies `--append-system-prompt-file` (`claude.mjs:1396-1398`), `--tools` + `--strict-mcp-config` (1412) and `--disallowed-tools Agent` (1415-1416) on every launch, resume included (1419). It verifies the permission mode (508-510, 873-875). Its in-process restart for effort changes reuses `staticArgs` (1417, 1438-1443), so it keeps the flags.
  - Codex passes `threadParams` (instructions, permissions, `features.multi_agent=false`) to `thread/resume` too (`codex.mjs:1320-1336`). It verifies the effective sandbox (1353-1368). It cannot re-register dynamic tools on resume (`codex.mjs:48-54`), which is irrelevant for a tool-less sidekick.
  - Pi / Prime / Hermes / ACP resume semantics were not read here.

### 3.3 Suppressing board and plugin injection

- **Board.** Add an explicit field `host_tools_policy: HostToolsPolicy::{Ordinary, None}` to `RuntimeStartOptions` (default `Ordinary` in `ordinary_open` and the launch request). In `spawn_pending` (1544-1554) skip `board_setup` entirely when `None`, so `board = None`, `host_tools = []`, and `LiveState.board = None` (1700-1710). Do **not** rely on `BoardBinding.run_id`; `setup_for` attaches the tool regardless of `run_id` (`board_sessions.rs:62-64`). Do not merge board instructions. `HostTool` (`crates/piui-runtime/src/workspace_runtime.rs:850-853`) has only `Board`; the lead's `sidekick` tool is a new variant that the sidekick must never receive (no recursion).
- **Plugin MCP.** `plugin_mcp_servers` (1086) already returns empty when `managed` is true. Passing `allowed_tools: Some(..)` makes `managed` true (1538-1540). Claude's bridge also throws if plugin servers are combined with an allowlist (`claude.mjs:112-114`), and `valid_session_mcp` rejects it in Rust (`workspace_runtime.rs:2530-2533`). So the allowlist is a double lock. Still add an explicit `plugin_mcp: Disabled` for clarity and for harnesses where `allowed_tools` is not enforceable.
- **User MCP servers and Agent tool (Claude).** `--strict-mcp-config` is added only when an allowlist exists (`claude.mjs:1412`). The sidekick therefore **must** carry an explicit Some allowlist. The frozen record should reject `allowedTools: None` at admission.
- **Native subagents.** `native_subagents: Some(false)` gives `--disallowed-tools Agent` (`claude.mjs:115,1415`) and Codex `features.multi_agent=false` (`codex.mjs:1325`). For Claude, whether `Agent` also blocks a legacy `Task` alias on the installed CLI is unverified (`claude.mjs:99` treats both names as the same tool).
- **bridge change needed for the lead's tool.** `claude.mjs:1409` pre-approves only the coordinator and board MCP tools, and 1415 denies `mcp__*` when an allowlist exists with no host tool. A `sidekick` host tool needs its own enable flag in both places or a lead with an allowlist would lose it.

### 3.4 WebView commands that must reject a sidekick session id

Introduce `HostState.workspace.is_sidekick(session_id)` (an in-memory lookup in the store) and a single helper `reject_sidekick(host, id)?`. Call it in each place below, after `validate_session_id`.

| Command | Where | Action |
|---------|-------|--------|
| `OpenSession` | `workspace_api.rs:3225` / `prepare_open` 1363 | **Reject** (`not_supported`), same shape as the `run_id` guard at 1374. Otherwise it would reach `ordinary_open`, so this is the critical one. |
| `Send` | `workspace_api.rs:3240` | Reject. |
| `workspace_composer_v19` (all verbs) | `workspace_composer.rs:545` | Reject; extend the existing `run_id` guard. |
| `workspace_composer_inputs_v1` Catalog | `workspace_composer_inputs.rs:373` | Reject. |
| `SetModel`, `workspace_settings_v16` Set | `workspace_api.rs:3260`, 2655 | Reject. Model is frozen and Claude effort changes restart with the same args; Codex model and mode changes are native runtime settings and would bypass freeze. Allow `Get` only if the UI shows it. |
| `workspace_session_mode_v1` | `workspace_api.rs:2748` | Reject (ACP only today). |
| `RenameSession` | `workspace_api.rs:3271` | Reject (broker owns the title; rename writes to the native session, 1959-1981). |
| `CreateSession` / placement `create_chat` | 3183, `placement_api.rs:575` | No sidekick id is accepted. Unchanged. Make sure `Shared { session_id }` and `continued_from` (`placement_api.rs:595,620`) reject a sidekick as source. |
| `Respond` | `workspace_api.rs:3278` | Allow only if the lead's UI surfaces sidekick approvals. In strict modes the Claude bridge offers only deny/cancel (`claude.mjs:1048-1050`). Reject `approve-session` for a sidekick, because that applies permission suggestions at runtime, which widens policy beyond the frozen record (effect unverified). |
| `Interrupt`, `CloseSession` | 3249, 3254 | Allow or route through the broker. Closing is harmless because the broker reopens from the store. |
| `Snapshot`, `workspace_history_v1`, review | 3157, 3115, `review_api.rs:232` | Read-only; fine to allow (useful for a "view sidekick transcript" UI). |
| `DeleteSession` (`workspace_lifecycle_v17`) | 3055-3097 | Reject for direct use (extend the `run_id` guard at 3067). The broker deletes it with the lead. |
| Board link / handoff (`board_command_v1`) | `board/mod.rs:250-258` | Reject a sidekick as `linked_session`. |
| `pipeline_library` save-from-session | `pipeline_library.rs:639-641` | Reject (extend `session_is_run`). |
| `Catalog` listing | `workspace_api.rs:1820-1846` | Filter sidekick rows out of the sidebar list (each registry row maps to `session_from_record`). |
| History / terminal catalog | `search_sessions`, `get_timeline_page` | The native transcript lives in the harness' own history roots. Whether the index shows it as an ordinary history entry was not traced. |

Trust revocation (`shutdown_workspace`, 2274-2291) and app exit (`shutdown_all`, 2295) already close every live session by registry id. A sidekick is included automatically.

### 3.5 Test sketch (for the plan, not run)

- Reopen after host restart restores the same instructions, permission, allowlist and no host tool: a Claude fixture asserting `--append-system-prompt-file`, `--tools`, `--strict-mcp-config`, `--disallowed-tools Agent` and the absence of `--allowed-tools mcp__piui-workspace__board`.
- Every WebView verb above returns `not_supported` for a sidekick id.
- The lead narrows its permission, then the sidekick refuses to reopen at its old mode.

## Conclusion

- Four production paths create or reopen a published native session (rows 1-4), plus two transient processes that never publish one (rows 5-6). Only the scheduler path freezes policy; it does so by re-deriving from the durable run snapshot at launch. Ordinary create/reopen supply no restrictions, and every path through `spawn_pending` injects board and plugin MCP unless `run_id` or `managed` says otherwise.
- Managed runs do not reopen across restart; they go Uncertain and refuse the ordinary reopen route. The broker-owned reopen is new work.
- Minimal design: a broker-owned `SidekickStore` side table, a `prepare_sidekick_open` building `RuntimeStartOptions` from it, an explicit `host_tools_policy` / `plugin_mcp` switch in `spawn_pending`, an always-Some allowlist, and a single `reject_sidekick` guard on the WebView verbs listed above.
