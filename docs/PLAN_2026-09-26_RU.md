# PiUI: план развития под новое видение

Дата: 26 сентября 2026. Основание: изучены код (Rust-хост и крейты, мосты харнесов,
Svelte-фронтенд, контракты), документация и ADR, нативные скриншоты интерфейса,
текущие незакоммиченные правки, а также внешние источники: Codex desktop, Claude Code,
ACP, DeepSeek Harness, Pi, n8n/Dify и похожие продукты (ссылки — в приложении A).
Код при подготовке плана не менялся. Проверка на момент написания: `svelte-check` —
0 ошибок, unit-тесты — 226/226 (47 файлов) с учётом незакоммиченных правок.

## 0. Коротко

- **Ядро у PiUI сильное** — его стоит сохранить: нативные адаптеры четырёх харнесов,
  контейнмент процессов, долговечная оркестрация с восстановлением, нативная история
  как источник правды, safe mode, доверие проектам.
- **Главный разрыв — интерфейс и модель пайплайнов.** Интерфейс инженерный: формы,
  внутренний жаргон, тулбары съедают холст; нет Home-композера, диффов, вложений,
  «Входящих». В графе только ноды «агент» и «роутер»: нет LLM-вызовов, скриптов,
  циклов с лимитом, Map, входных данных запуска.
- **Расширяемость в основном на бумаге.** Плагином нельзя добавить ни харнес, ни ноду,
  ни рендер. Харнесы — закрытые enum: подключение Hermes затронуло 88 файлов.
- **Стабильность** упирается в конкретные места: квадратичный стриминг без
  виртуализации, стор оркестрации переписывается целиком под общим мьютексом,
  глобальный гейт блокирует одобрения, версии харнесов пришиты точно, а CI проверяет
  скрытый classic-интерфейс вместо основного.
- **Рекомендация — гибрид:** ядро развиваем, фронтенд пересобираем на дизайн-системе
  (Svelte 5 runes, bits-ui, Svelte Flow). Харнесы переводим на открытый реестр и
  универсальный ACP-адаптер: он сразу открывает Claude Code, Gemini CLI, OpenCode, Kimi,
  Qwen, DeepSeek Harness и другие. Пайплайны становятся первичным документом v5 с
  каталогом нод. Дальше — наблюдение как в n8n, ИИ-конструктор в приложении и открытие
  реестров плагинам.
- **Порядок работ:** Ф0 стабилизация → Ф1 дизайн-система → Ф2 чат ∥ Ф3 харнесы →
  Ф4 пайплайны → Ф5 наблюдение → Ф6 ИИ-конструктор → Ф7 триггеры → Ф8 плагины → Ф9 релиз.
- **От тебя нужны решения** по девяти вопросам (§13). Главные: стратегия, политика
  плагинов, способ подключения Claude Code, скрипт-ноды.

## 2. Что уже есть и что сохранить

Проект сильнее, чем выглядит снаружи. Ядро закрывает трудные вещи, которые у
«красивых» конкурентов часто сделаны плохо:

- **Нативные адаптеры четырёх харнесов**: Pi RPC, общий Codex app-server, Prime SDK,
  Hermes ACP. Они работают через host-owned Node-мост с контейнментом процессов
  (Windows Job Objects / process groups) и поддерживают одобрения, прерывание,
  steer/follow-up, компактизацию и нативные каталоги моделей.
- **Нативная история как источник правды**, переоткрытие и resume, черновики чатов.
- **Долговечная оркестрация**: снимки запусков, журнал с ревизиями, восстановление через
  состояние «неизвестно» вместо слепого повтора, одобрения, роутеры, review-циклы,
  типизированные результаты, артефакты. Есть динамические агенты (`spawn_agent`/`wait`)
  с проверкой, что ребёнок не получает больше прав, чем родитель.
- **Расписания** (разово/интервал), **Agent API** для внешних агентов, скилл
  **`piui-systems`** для генерации систем из текста, импорт/экспорт `*.piui.json`
  с общим валидатором.
- **Дисциплина**: safe mode, generic fallback, доверие проектам, контрактные тесты,
  нативный E2E на WebView2, проверки контраста палитры.

Масштаб: Rust ≈ 53 тыс. строк, мосты ≈ 4 тыс., фронтенд ≈ 17,5 тыс. (очень плотных)
строк, 81 Tauri-команда, 40 файлов контрактов, ≈ 840 КБ документации.

## 4. Стратегия: переписывать ли всё

**Рекомендация — не переписывать с нуля: ядро сохранить и развить, интерфейс пересобрать.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Полный rewrite | Чистый лист | Теряем месяцы выстраданного (контейнмент, восстановление, нативные адаптеры, журнал); долго нет рабочего продукта |
| Только эволюция | Непрерывность | UI-долг и сверхплотный код останутся; закрытые enum тормозят каждый новый харнес |
| **Гибрид** | Сохраняем ценное ядро и быстро получаем новый UI | Нужна дисциплина миграции по экранам |

- **Сохраняем и развиваем:** Rust-хост, контейнмент, мосты харнесов (→ Harness SDK),
  координатор оркестрации (→ новые исполнители), индекс, доверие, safe mode.
- **Пересобираем:** весь фронтенд-shell на дизайн-системе и Svelte 5 runes, редактор
  графа — на Svelte Flow, модель пайплайна — v5 с миграцией.
- **Удаляем:** classic-интерфейс и его отдельный хост-путь, мёртвые версии контрактов
  и команды, дубли проверок графа в TS.

```
┌──────────────────────────── WebView (Svelte 5, runes) ────────────────────────────┐
│ Оболочка: Сайдбар · Home/Чат · Редактор пайплайнов (Svelte Flow) · Запуски ·       │
│ Входящие · Настройки │ Дизайн-система (токены + bits-ui) │ iframe плагинов (sandbox)│
│ host-api: сгенерированные из Rust типы, единая модель ошибок, домены-сторы         │
└──────────────────────────────────┬─────────────────────────────────────────────────┘
                                   │ allowlist Tauri-команд + типизированные события
┌──────────────────────────────────▼──────────────── Rust-хост ──────────────────────┐
│ Приложение: проекты · чаты · пайплайны · запуски · автоматизации · плагины         │
│ Реестр харнесов (дескрипторы) │ Движок пайплайнов (координатор + исполнители)       │
│ Брокер плагинов               │ Хранилище оркестрации (SQLite WAL, авторитетное)   │
│ Индекс истории (SQLite, кэш)  │ Платформа: контейнмент, watch, уведомления, трей   │
└──────┬──────────────┬──────────────┬──────────────┬──────────────┬─────────────────┘
       │ Node-мост    │ Node-мост    │ Node-мост    │ Node-мост    │ процессы плагинов
   pi --mode rpc  codex app-server  Prime SDK   ACP-адаптер       харнесы, ноды,
                                                 Claude Code,      MCP-серверы
                                                 Gemini, OpenCode,
                                                 Hermes, DeepSeek…
```

- LLM-ноды исполняются через one-shot режим адаптера харнеса. Своих провайдер-клиентов
  в PiUI по-прежнему нет.
- Скрипт-ноды запускает хост в контейнменте, как и процессы харнесов.
- ИИ-конструктор — это обычная сессия выбранного харнеса плюс MCP-endpoint PiUI Builder,
  который хост выдаёт этой сессии. Механизм уже используется для координатора Hermes.

## 6. Целевой UX

### 6.1 Информационная архитектура: один мир вместо «Sessions | Workspace»

Сейчас приложение разделено на два режима с дублирующимся списком проектов. Внутри
оркестрации живут внутренние понятия: definition, profile, team, pipeline, launch
command, recorded run, coordinator, execution mode. Пользователь думает проще:
«проект → чаты и пайплайны → запуски».

```
┌ Сайдбар ─────────────┐┌ Основная область ──────────────────┐┌ Правая панель ─────────┐
│ ＋ Новый чат  Ctrl+N │ │ Home / Чат / Пайплайн / Запуск     │ │ Ревью · Детали ·       │
│ ⌕ Поиск       Ctrl+K │ │                                    │ │ Инспектор ноды · Логи  │
│ ◉ Входящие (2)       │ │                                    │ │ (плагины: терминал…)   │
│ ▾ Проект A           │ │                                    │ │                        │
│    чат 1   ● идёт    │ │                                    │ │                        │
│    чат 2             │ │                                    │ │                        │
│    ⎇ Пайплайны (3)   │ │                                    │ │                        │
│ ▸ Проект B           │ │                                    │ │                        │
│ ▸ Личные чаты        │ │                                    │ │                        │
│ ⟳ Запуски            │ │                                    │ │                        │
│ ⏱ Автоматизации      │ │                                    │ │                        │
│ ▣ Библиотека         │ │                                    │ │                        │
│ ⧉ Плагины ⚙ Настройки│ │                                    │ │                        │
└──────────────────────┘ └────────────────────────────────────┘ └────────────────────────┘
```

- **Входящие** — единая очередь того, что ждёт человека: одобрения команд, вопросы
  агентов, human-ноды пайплайнов, упавшие запуски, результаты автоматизаций (у Codex
  для этого есть отдельный inbox «Scheduled»). В мультиагентной работе это главный
  экран внимания; сейчас одобрения разбросаны по чатам и запускам.
- **Пайплайн** — один объект вместо «система / профили / команда / pipeline / launch
  command». Агенты-шаблоны живут в **Библиотеке** и добавляются в пайплайн копией или
  ссылкой, причём видно, чем именно.
- **Запуски** — общая лента с фильтрами по проекту, пайплайну, статусу и времени, с ID.
- **Автоматизации** — расписания и событийные триггеры всех пайплайнов в одном месте.

### 6.2 Чат уровня Codex

**Home (новый чат).** Вместо формы «Create session» по центру стоит композер
«Что делаем?». Над ним чипы: проект · харнес · модель + reasoning · режим прав ·
Локально/Worktree. Чат создаётся при первой отправке. Ниже — недавние чаты, шаблоны
пайплайнов и активные запуски.

**Лента.**
- Сообщения пользователя — компактные нейтральные «пузыри». Ответ — чистый Markdown
  в колонке ~760–820 px (сейчас `104ch`, для чтения слишком широко).
- «Думал 12 с» — свёрнутое reasoning.
- Группы действий: «Выполнил 4 команды · изменил 3 файла». В развороте у команды видны
  cwd, код выхода и вывод, у файла — настоящий diff-вьюер (unified/split), а не текст.
- План и todo харнеса (план Codex, TodoWrite у Claude) — живой чек-лист.
- Одобрение — карточка прямо в ленте с понятным описанием и кнопками «Разрешить один
  раз / на сессию / Отклонить»; та же карточка дублируется во «Входящих».
- Ошибка — карточка с причиной и кнопками «Повторить» и «Открыть логи».
- Под каждым ходом — футер: модель, токены, длительность (где харнес их отдаёт).
- Дочерние агенты: из активности родителя открывается транскрипт ребёнка (как в Codex).
- Длинные сессии — виртуализация и постраничная подгрузка (§10).

**Композер.**
- Многострочный ввод, вложения: вставка и перетаскивание картинок и файлов, если
  харнес это поддерживает.
- `@` — файлы проекта (нечёткий поиск), агенты, пайплайны. `$` — скиллы.
- `/` — **динамические** команды харнеса (у Pi есть RPC `get_commands`) плюс команды
  PiUI и плагинов. Сейчас список захардкожен: `/compact` и `/stop`.
- Чипы: модель (Ctrl+Shift+M, как в Codex), reasoning (сегменты из нативного каталога),
  Fast (где есть), режим прав.
- Отправка, стоп, очередь и Steer — уже есть, сохранить.

**Режимы прав с одинаковыми названиями для всех харнесов:** «Спрашивать / Авто /
Полный доступ». Каждый режим отображается на нативные режимы конкретного харнеса;
где соответствие неточное, это видно в интерфейсе. Нативная capability остаётся
источником правды.

**Правая панель.**
- **Ревью (Ctrl+Alt+B):** изменения рабочей копии и последнего хода, stage/revert файла
  или ханка, комментарий к строке уходит агенту как замечание (паттерн из Codex).
- **Детали** человеческим языком (вместо «History revision» и «NativeSubagents: Native»),
  связанный запуск и пайплайн.
- Позже — плагинами: терминал чата, файлы, превью, браузер.

**Worktree-режим:** параллельные чаты работают в отдельных git worktree, есть «Перенести
в локальную копию» (как Worktree/Hand off в Codex). Это особенно важно для пайплайнов,
где несколько кодовых агентов работают одновременно.

**Мелочи, из которых складывается ощущение Codex.**
- Ctrl+K — палитра по чатам, пайплайнам и командам; Ctrl+N; Esc — стоп; горячие
  клавиши показаны в подсказках.
- Системные уведомления: ход завершён, нужно одобрение, запуск упал.
- Переименование прямо в заголовке, закрепление, архив.
- «Продолжить в другом харнесе»: новый чат со сводкой, которую пользователь согласовал.
  Историю не конвертируем.
- Скелетоны вместо «Loading…», пустые состояния с одним понятным действием, переходы
  150–200 мс с уважением к reduced motion.

### 6.3 Харнес → модель → reasoning

- Новый чат: чип харнеса показывает установленные и готовые харнесы, рядом статус
  («нужен вход», «не установлен» → ссылка в Настройки → Харнесы).
- Существующий чат: харнес фиксирован, потому что история нативная. Модель, reasoning
  и Fast меняются между ходами — это уже работает через нативные каталоги.
- Нужно добавить reasoning и Fast в запрос создания сессии. Нативный конфиг их уже
  поддерживает, но контракт создания не передаёт, и хост отправляет `None`.
- Один компонент ModelPicker для чата, ноды графа и библиотеки: поиск, группы по
  провайдеру, бейджи возможностей (reasoning, fast, vision), недоступные модели —
  с причиной.

### 6.4 Редактор пайплайнов

Сейчас над холстом 3–4 ряда кнопок и `<details>`-меню, и холсту остаётся меньше
половины экрана. Цель — как в n8n, где холст занимает почти весь экран.

- **Одна верхняя полоса:** имя, статус черновика, «Проверить», «Сохранить», «▶ Запустить»
  и меню «⋯» (импорт, экспорт, дубликат, версии).
- **Палитра нод:** кнопка «＋», `Tab` на холсте, ПКМ по холсту; если перетащить связь
  с порта в пустоту, открывается поиск ноды. Категории: Триггеры · ИИ · Логика ·
  Действия · Человек · Плагины.
- **Нижняя плавающая панель:** зум, fit, авто-раскладка, мини-карта, отмена/повтор.
- **Карточка ноды:** иконка типа, имя, харнес и модель (для ИИ-нод), одна строка задачи,
  порты с подписями полей. В режиме запуска на карточке показаны статус, счётчики
  итераций и экземпляров, токены.

  наблюдение, делегирование) — отдельный переключаемый слой пунктирных связей.
- Группы, рамки и заметки на холсте; копирование нод между пайплайнами; мульти-выделение.
- **Панель «Проблемы»** (проверка + линтер): клик переводит к ноде и нужному полю.

## 7. Пайплайны v2

### 7.1 Главный сдвиг: пайплайн — сохраняемый документ, а не производная

Сейчас граф компилируется в profiles/team/pipeline/launch command и обратно
декомпилируется при открытии. Позиции нод живут только в localStorage, часть форм
графа открыть нельзя. `save_graph` оставляет профили удалённых нод, а UI сам угадывает
новые ревизии. Нужно наоборот:

- **Pipeline Document** — первичный объект (JSON, схема v5): ноды, связи, входы и выходы
  пайплайна, триггеры, слои, заметки, позиции, лимиты. Хранится атомарно с ревизией;
  экспорт и импорт — тот же документ (`*.piui.json` v5).
- **Версии:** черновик и опубликованная версия. Расписания и запуски из чата используют
  опубликованную (как агенты в n8n).
- **Профили агентов** — шаблоны в Библиотеке; нода содержит копию или ссылку, и это видно.
- **Run** замораживает снимок документа и **входные данные запуска**. Сейчас запуск
  не принимает входа вообще, поэтому задача «зашита» в текст ноды.
- **Миграция:** файлы и сохранённые системы v1–v4 → v5. Агент → Агент, `callable` → Роль,
  router → Switch, review → Цикл с `maxIterations`, launch command → ручной триггер.

### 7.2 Каталог нод и правило «осмысленной ноды»

Нода оправдана, если выполняется хотя бы одно из условий:
1. меняется **исполнитель** — другой харнес, модель, права или инструменты;
2. нужна **проверка** — детерминированная, человеком или независимым агентом;
3. меняется **поток управления** — ветвление, слияние, цикл, параллель;
4. результат нужен **нескольким потребителям**, или его надо отдельно видеть и закреплять.

Иначе это шаг внутри инструкций агента. Правило проверяет линтер «Доктор графа».
Он предупреждает о таких ситуациях:
- **перегруженный агент:** несколько независимых результатов, разнородные инструменты,
  очень длинные инструкции → предложить разделить;
- **дробление без смысла:** две последовательные ноды с тем же исполнителем, без
  проверки и ветвления → предложить слить;
- цикл без выхода; неограниченный fan-out; неиспользуемый выход;
- поле не совпадает со схемой входа.

| Категория | Нода | Что делает | Сейчас |
|---|---|---|---|
| Триггеры | **Ручной / Форма** | Входные поля пайплайна (текст, файл, папка, выбор…), форма при запуске | нет, запуски без входа |
| | **Чат** | Запуск из чата (`@пайплайн`, `/run`): сообщение и вложения → входы, итог → в чат | нет |
| | **Расписание** | cron, интервал, разово; часовой пояс | только once/interval |
| | **Событие** (плагины) | Изменение файлов, git-коммит, завершение другого пайплайна, локальный webhook | нет |
| ИИ | **Агент** | Нативная сессия харнеса с инструментами | есть |
| | **Роль** (вызываемый шаблон) | Сама не планируется; экземпляры создаёт оркестратор | есть как `callable`, без лимитов и визуализации |
| | **LLM** | Промпт-шаблон → текст или JSON по схеме, без инструментов, через one-shot режим харнеса. Пресеты: «Классификатор», «Извлечь поля», «Резюме» | нет |
| Логика | **Switch** | Ветвление по правилам или решению агента | есть (router) |
| | **Цикл** | Контейнер: повторять вложенный подграф до условия выхода или `maxIterations`; нода «Выйти из цикла» | частично (review, без лимита) |
| | **Для каждого (Map)** | Список → N веток с лимитом параллельности → список результатов; режимы ошибок: стоп / продолжить / отбросить упавшие | нет |
| | **Слияние** | Ждать все / любой / первые N; объединить | только AND |
| | **Преобразование** | Декларативное сопоставление полей и шаблон — без LLM и без кода | нет |
| Действия | **Скрипт** | JS/TS, Python, shell: stdin JSON → stdout JSON в каталоге проекта, в контейнменте, с таймаутом | нет |
| | **Подпайплайн** | Вызов другого пайплайна с входами → выходы; «Превратить выделенное в подпайплайн» | нет |
| | **HTTP** (плагин) | Запрос к API | нет |
| Человек | **Одобрение** | Принять или отклонить с комментарием; отклонение ведёт в ветку возврата | флаг на шаге |
| | **Вопрос / форма** | Спросить данные у человека посреди запуска, с таймаутом | нет |
| Выход | **Результат** | Выходы пайплайна: в чат, файл, уведомление | неявно |

**Обработка ошибок** — на каждой ноде: «остановить», «значение по умолчанию» или
«ветка ошибки» (как в Dify). На пайплайн можно назначить пайплайн-обработчик ошибок
(как Error workflow в n8n). **Сниппеты** — переиспользуемые группы нод.

### 7.3 Связи и данные

- **Поток** (сплошная линия): выход → вход. Несёт данные и задаёт порядок.
- **Коммуникации** (пунктир, отдельный слой): сообщения, наблюдение, право создавать
  экземпляры роли. Порядок не задают — это различие сохраняем.
- **Конверт результата** каждой ноды: `{ text, json?, artifacts[], nativeRef, usage }`.
  `nativeRef` указывает в нативную историю, так что источник правды не меняется.
- **Сопоставление полей.** В инспекторе есть панель «Входы»: поле выхода предыдущей
  ноды можно перетащить (как в n8n). Работают безопасные шаблоны
  `{{ nodes.Planner.json.tasks }}`, `{{ trigger.topic }}`, `{{ loop.iteration }}`,
  `{{ item }}`. Язык выражений маленький, без `eval` и вызова кода; вычисляется в Rust,
  в UI показывается превью. Сейчас данные передаются склейкой текстов «dependency N»
  или JSON-биндингами.
- **Схемы входов и выходов** (подмножество JSON Schema) в «Основном» необязательны,
  но обязательны там, где их нужно проверять: Switch, Map, выход цикла.
- **Изоляция рабочей копии** для кодовых агентов: общий каталог или git worktree на
  каждый экземпляр, плюс нода «Слить изменения» с ревью диффа (как Worktree в Codex,
  Crystal, Conductor, Emdash). Без этого параллельные рабочие конфликтуют в файлах.

### 7.4 Твои сценарии в новой модели

**Оркестратор решает, сколько нужно рабочих и тестировщиков.**
```
[Ручной: задача] → [Агент «Оркестратор»] ─ ─ может создавать ─ ─▶ (Роль «Рабочий», ≤5, параллельно 3)
                          │                ─ ─ может создавать ─ ─▶ (Роль «Тестировщик», ≤3)
                          ▼                   отчёты ролей → Оркестратор или «Ревьюер»
                   [Результат]
```
Во время запуска у роли видна стопка экземпляров «×4 (3 ✓, 1 ⟳)»; по клику открывается
список и транскрипт каждого экземпляра. Оркестратор видит в `roster` оставшуюся ёмкость.
Лимиты — пользовательские настройки роли и пайплайна: экземпляры, параллельность,
глубина, бюджет времени и токенов. Решить отдельно, чтобы падение одного ребёнка
не отменяло всю готовую к запуску работу, как сейчас.

**Цикл до результата (A → B → C → A).**
```
┌─ Цикл: до «C.json.status == done», максимум 5 ─────────────────┐
│ [Агент A: разработчик] → [Агент B: тесты] → [Агент C: ревью]   │
└────────────────────────────────────────────────────────────────┘
```
A получает замечания прошлой итерации через `{{ loop.previous.C.json.notes }}`.
Опция ноды «Продолжать диалог между итерациями» сохраняет нативную сессию и её контекст.

**Детерминированный конвейер без лишних агентов.**
`Форма (видео, бриф) → LLM «план сцен» (JSON) → Для каждого: сцена {Агент «монтажёр» →
LLM «проверка по брифу»} → Слияние → Скрипт «склейка ffmpeg» → Одобрение → Результат`.

### 7.5 Исполнение: Rust-координатор развиваем, а не переписываем

- **Новые исполнители:** LLM one-shot (через адаптер харнеса); Скрипт (контейнмент как у
  харнесов, таймаут, лимит вывода); Преобразование; Слияние; Цикл и Map (итерация и индекс
  элемента входят в ключ задачи журнала); Подпайплайн; Human.
- **Политики:** `maxIterations`; экземпляры и параллельность ролей; таймаут ноды;
  авто-повтор с backoff (явная настройка, по умолчанию выключен); бюджет запуска.
  Никаких «зашитых» лимитов — только явные настройки, как требуют текущие правила.
- **Надёжность журнала:** вместо «склонировать весь стор и переписать файл на каждый
  переход под общим мьютексом» — транзакционное хранилище (отдельный SQLite
  `orchestration.db` в WAL: это авторитетные данные, а не кэш). Нужны также удаление
  и архивация запусков, блокировки на уровне запуска вместо одного глобального мьютекса
  и async-команды вместо синхронных на main thread.
- Ручные запуски после перезапуска продолжаются так же, как запланированные.
- **Одна реализация проверок графа** — в Rust; UI получает превью через хост. Сейчас
  есть шесть копий проверки циклов и топосортировки в TS и Rust, и они расходятся
  (например, TS не проверяет сеть при делегировании).
- **События:** вместо `runChanged → перечитать весь Run` — инкрементальные события
  (нода стартовала, выход, статус, расход) с ревизиями и догрузкой при разрыве.

## 8. Платформа харнесов

### 8.1 Открытый реестр вместо закрытых enum

Подключение Hermes затронуло 88 файлов (+3991/−372). Собственно логики Hermes там
около 18%, а примерно 70% — механика: новое значение в закрытом `Harness` потребовало
новых версий шести контрактов и переименования всех команд (`_v11→_v15` и т.д.). При
такой схеме каждый новый харнес — это неделя churn.

- `HarnessId` становится строкой. Serde уже пишет kebab-case, поэтому старые журналы
  читаются как есть.
- **Дескриптор харнеса** на стороне хоста:
  - id, имя, иконка;
  - транспорт: `pi-rpc` | `codex-app-server` | `prime-sdk` | `acp` | `claude-sdk` | плагин;
  - обнаружение, проверка версии и диапазон совместимости;
  - capability-манифест;
  - политика прав (сейчас `harness_configuration.rs`);
  - формат нативной истории и её проектор.
- Около 25 `match`-точек в Rust, `Record<Harness,…>` и `assertNever` в TS заменяются
  запросами к реестру. Манифесты для UI отдаёт хост; сейчас они продублированы в
  `src/harness-adapters`, в том числе списки инструментов.
- Встроенные харнесы регистрируются тем же способом, каким будут регистрироваться плагинные.

`bridge/CONTRACT.md` — хорошая основа. Его нужно довести до публичного SDK с такими

### 8.3 Универсальный ACP-адаптер

ACP (Agent Client Protocol, v1) нативно поддерживают Gemini CLI, OpenCode, Goose, Hermes,
Cursor, GitHub Copilot, Kimi CLI, Qwen Code, Junie, Kiro, Cline, OpenHands, Mistral Vibe.
Через адаптеры его поддерживают Claude Code (`claude-agent-acp`), Codex (`codex-acp`)
и Pi (`pi-acp`); у DeepSeek Harness есть собственный `acp`-профиль. В стабильной схеме
модель и уровень рассуждений выбираются через `session/set_config_option` (категории
`model`, `thought_level`), так что выбор модели и reasoning в чате работает для всех
ACP-агентов.

В `hermes.mjs` уже есть почти готовое ядро ACP: JSON-RPC по stdio, initialize,
session/new|load, маппинг update-событий, permissions, cancel, HTTP MCP для координатора.
План:
- выделить `acp.mjs` и профиль агента: argv/env, проверка версии, источник моделей,
  хуки meta/outcome, проектор истории;
- добавить `authenticate`, согласование capabilities (`loadSession`, MCP), config options
  вместо `set_model`, клиентские `fs/*` и `terminal/*` (опционально, с правами), диффы,
  терминалы, план и режимы в маппинге, `allow_always`.

После этого новый ACP-агент подключается дескриптором, без кода. Для Pi и Codex
оставляем нативные адаптеры: они богаче.

### 8.4 Claude Code

Своего агентного цикла не пишем ни в одном из вариантов.

1. **Через ACP-адаптер** `@agentclientprotocol/claude-agent-acp` (Apache-2.0, построен на
   Agent SDK). Уже умеет @-упоминания, изображения, запросы разрешений, ревью правок,
   TODO, терминалы, слеш-команды, клиентские MCP и вложенные транскрипты субагентов.
2. **Через нативный мост на Claude Agent SDK.** Даёт больше контроля: `supportedModels()`,
   `setModel()`, `effort`, `setPermissionMode()`, `canUseTool` для одобрений, хуки,
   инъекцию MCP-координатора, `settingSources` (CLAUDE.md, скиллы, агенты пользователя),
   resume и fork по session id. Историю читать через `getSessionMessages()`, а не
   разбором JSONL: формат транскриптов внутренний и меняется между версиями.
   Транскрипты по умолчанию удаляются через 30 дней (`cleanupPeriodDays`). PiUI должен
   корректно показывать пропавшую историю и не менять чужой конфиг.

Рекомендация: чаты подключить через (1), для графов сделать прототип (2) и перейти на
него, если ACP-профиль не даёт нужных capabilities.

**Решение владельца (26.09.2026): Claude Code работает только по подписке.** Агенты
пайплайнов на Claude Code запускаются так же, как в Codex, — под той же подпиской.
Требования к адаптеру:
- запускается установленный пользователем немодифицированный `claude` (без `--bare`,
  который требует API-ключ); при SDK-пути — `pathToClaudeCodeExecutable` на этот бинарник;
- из окружения процесса вычищаются `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`,
  `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` и родственные
  переменные, чтобы CLI не переключился на ключ или облачного провайдера;
- по событию `system/init` проверяется источник авторизации (`apiKeySource`): всё, кроме
  входа подпиской, — отказ с понятной подсказкой «войдите в Claude Code своей подпиской»;
- вход выполняется только нативным флоу Claude Code (кнопка открывает терминал с `claude`),
  PiUI не читает, не копирует и не хранит учётные данные;
- в интерфейсе видны лимиты подписки (события rate limit), параллельные агенты расходуют
  общий лимит — лимиты экземпляров ролей особенно важны.

**Юридический нюанс — проверить до публичного релиза.** По документации Agent SDK
сторонним разработчикам без согласования Anthropic нельзя предлагать в своих продуктах
вход через claude.ai и лимиты подписки. Собирать, хранить или проксировать учётные данные
Claude.ai тоже нельзя. При этом пользователю не запрещено входить своей подпиской
в немодифицированный бинарник Claude Code. Отсюда модель для PiUI:
- запускается установленный пользователем `claude`;
- вход выполняется его собственным флоу;
- учётные данные PiUI не трогает;
- режим с API-ключом доступен как чистая альтернатива.

Сообщалось о блокировках подписочных токенов в OpenCode (вторичный источник,
не проверено). Прежде чем полагаться на подписку в распространяемой сборке,
стоит спросить Anthropic.

### 8.5 Здоровье харнесов и совместимость версий

- Версии пришиты точно: Codex 0.147.0/0.153.4, Prime 0.9.2/0.9.3, Hermes 0.21.0.
  Обновил Codex — PiUI перестал с ним работать. Нужен **диапазон** версий, проверка
  capabilities при старте (у Claude Code, например, есть массив `capabilities` в
  `system/init`) и понятная деградация: «версия новее проверенной — работаем, X
  отключено», а не отказ.
- Hermes-адаптер опирается на monkeypatch приватных внутренностей Python. При переходе
  на универсальный ACP этот хак нужно убрать.
- `platform_verified = cfg!(windows)` помечает все харнесы вне Windows как непроверенные
  и отключает создание сессий. Корни npm захардкожены. Нужны реальные проверки платформы.
- Для Pi учитывать, что завершение хода — `agent_settled`, а не `agent_end`. В RPC есть
  `fork`, `clone`, `get_tree`, `switch_session`, так что навигацию по дереву сессии
  (риск R-03) можно пересмотреть.

## 9. Плагины

### 9.1 Что есть сейчас

Спецификация расширений большая: Tier 0–3, слоты, рендеры, темы, rich views. Реализовано
и достижимо мало:
- Валидатор манифеста есть. Проецируются только команды `pi-command:*` и кнопки
  композера («Tier 1A»), и **только в classic-интерфейсе**, который из основного
  приложения не открывается. Собственный пример пакета в репозитории не проецирует ничего.
- В основном интерфейсе слеш-команды захардкожены. `select`-диалоги расширений Pi
  фактически нельзя ответить: мост отбрасывает варианты. Переключатели глобальных
  расширений Pi/Prime есть только в classic-настройках.
- Новые ноды, харнесы, рендеры, панели, темы и горячие клавиши плагином добавить нельзя:
  enum закрыты, список команд статический, CSP запрещает iframe.

### 9.2 Цель: один плагин-API, на котором построены и встроенные функции

За образец берём DeepSeek Harness («всё — плагин», у инструментов есть UI-карточки с
generic-фолбэком, установка через `dsh plugin`, поиск по GitHub-топику) и API расширений
Pi (`registerTool`, `registerCommand`, `registerShortcut`, UI-диалоги, события).

**Манифест** `piui.plugin.json` (или поле `piui` в `package.json`):
```jsonc
{
  "id": "acme.video-tools",
  "version": "1.0.0",
  "engines": { "piui": "^2.0.0" },
  "permissions": ["process.spawn", "fs.project.read", "network:api.example.com"],
  "contributes": {
    "harnesses":  [{ "id": "gemini", "transport": "acp", "command": "gemini", "args": ["--experimental-acp"] }],
    "nodes":      [{ "id": "ffmpeg.render", "category": "actions", "inputs": {}, "outputs": {}, "config": {}, "executor": "backend" }],
    "mcpServers": [{ "id": "acme.search", "command": "node", "args": ["mcp/search.js"] }],
    "commands":   [{ "id": "acme.export", "title": "Экспорт в Premiere", "keybinding": "Ctrl+Alt+E" }],
    "renderers":  [{ "block": "mcp_tool", "match": { "tool": "ffmpeg.*" }, "view": "ui/render.html" }],
    "views":      [{ "slot": "rightPanel", "title": "Таймлайн", "view": "ui/timeline.html" }],
    "settings":   { "schema": "settings.schema.json" },
    "themes":     [{ "id": "acme.dark", "tokens": "themes/dark.json" }],
    "templates":  ["templates/*.piui.json"],
    "skills":     ["skills/*"]
  }
}
```

**Точки расширения, по убыванию ценности:**
1. **Харнесы** — ACP-агент одним дескриптором, сложный харнес — backend-адаптером по
   Harness SDK.
2. **Типы нод** — декларативная схема входов, выходов и настроек (инспектор строится
   автоматически) плюс исполнитель в backend-части плагина.
3. **Инструменты для агентов** — MCP-серверы плагина, которые включаются для агента
   или чата.
4. **Команды и горячие клавиши**, **настройки** (форма по JSON Schema).
5. **Рендеры блоков** (вывод инструмента, результат ноды) и **панели** (правая панель,
   вкладка запуска) — в изолированном iframe.
6. **Темы** (набор токенов), **шаблоны пайплайнов**, **скиллы**.

**Исполнение и безопасность** — в рамках уже принятых ADR-009/010/011/016:
- Backend-часть плагина — отдельный процесс (Node) под тем же контейнментом, что и
  харнесы, связь по JSON-RPC. Общих shell/fs API в WebView нет.
- UI-часть — только sandboxed iframe (без `allow-same-origin`, CSP хоста, postMessage
  через брокер с проверкой прав) или декларативные карточки и формы, которые рисует PiUI.
- Установка — отдельное окно доверия со списком прав. Проектные плагины грузятся
  только после доверия и проекту, и плагину. Смена отпечатка пакета отзывает опасные права.
- Safe mode выключает все плагины; у каждого рендера есть generic fallback.
- Говорим честно: backend-плагин работает с правами пользователя, это не песочница.

**Опыт разработчика:**
- `pnpm create piui-plugin` с шаблонами: ACP-харнес, нода-скрипт, рендер, тема;
- режим разработки «загрузить папку» с hot reload;
- типизированный `@piui/plugin-sdk`;
- страница «Плагины» с логами и перезапуском;
- документация с примерами.

### 9.3 Изменение правил и порядок

`AGENTS.md` сейчас прямо запрещает загружаемый в рантайме JS как плагин-API для
харнесов. Предлагаемая модель (вне WebView, с явным доверием, под контейнментом,
с safe mode) — осознанное изменение политики. Нужен отдельный ADR и твоё решение.

Открывать API наружу раньше, чем стабилизируются внутренние реестры, не стоит.
Сначала встроенные харнесы и ноды регистрируются через реестр (Ф3–Ф4), потом этот же
реестр открывается плагинам (Ф8). Так API проверяется на собственных функциях.

## 10. Стабильность и инженерия

### 10.1 Зависания и потеря работы — в первую очередь

| Проблема | Где | Что делаем |
|---|---|---|
| Стор оркестрации клонируется и переписывается целиком на каждый переход под std Mutex; часть команд синхронные и идут на main thread; запуски не удаляются → фризы растут со временем | `orchestration_store.rs`, `orchestration_api.rs` | Сразу: запись вне общего lock, async-команды, архив запусков. В Ф4: SQLite WAL |
| Глобальный operation gate держится во время старта сессии (у Hermes до 50 с) и блокирует прерывания и одобрения всех остальных сессий | `state.rs`, `workspace_api.rs` | Гейт на сессию; спавн вне общего гейта |
| Канал событий на 256 + `try_send`: переполнение считается ошибкой протокола и убивает рантайм, а в пуле Codex — все управляемые Codex-сессии | `workspace_runtime.rs`, `codex-pool.mjs` | Backpressure с коалесценцией дельт вместо убийства |
| Нет таймаута хода и `wait` — зависший ход висит вечно | мосты, планировщик | Настраиваемые таймауты с понятным состоянием |
| Реестр переписывается с fsync на каждое usage/binding-событие | `workspace_store.rs` | Батчинг записей |
| Ручные запуски не продолжаются после перезапуска приложения | `orchestration_scheduler.rs` | Та же логика, что у запланированных |
| Черновики UI в sessionStorage переписываются на каждое нажатие и теряются при перезапуске | `WorkspaceShell.svelte` | Хостовое хранилище черновиков с дебаунсом |

### 10.2 Производительность интерфейса

- **Стриминг квадратичный.** На каждый токен копируется весь массив блоков,
  пересортировывается сайдбар, заново группируется лента и парсится весь Markdown;
  батчинга через requestAnimationFrame нет (в classic он был).
- **Нет пейджинга и виртуализации.** Снапшот несёт все блоки из файла истории
  до 128 МБ.
- Что делаем:
  - батчинг дельт на кадр;
  - инкрементальный Markdown только для блока, который сейчас стримится;
  - постраничный снапшот;
  - виртуализированная лента;
  - перф-тест «длинная сессия» в CI.
- **Бюджет бандла на грани:** в HEAD 336 КБ при лимите 260 КБ, в рабочем дереве
  263 КБ (запас 1,2%). Решение — ленивые чанки редактора и валидаторов (сейчас
  `systemFile` тянет четыре ajv-валидатора, 141 КБ); сам бюджет считать в gzip.

### 10.3 Дефекты, найденные при чтении кода

- **Pi:** вывод инструментов не показывается, `select`-диалоги не отвечаются, блок
  компактизации не завершается.
- **Hermes:** сообщения между агентами (FollowUp) не доставляются; после ошибки промпта
  сессия навсегда `failed`; ACP отвечает `end_turn` даже при ошибке провайдера.
- **Codex:** MCP- и dynamic-вызовы отображаются как `unknown`.
- **Проверки графа** в TS расходятся с Rust: TS не проверяет сеть при делегировании
  и игнорирует route-связи в review.
- **Диалоги:** объявлены `aria-modal`, но не модальные; `<details>`-меню не закрываются
  по клику вне.
- **Ещё:** `rust-version` заявлен 1.85, а код требует 1.88+. Составные предикаты
  роутера нельзя редактировать в UI. `orchestratorMemberId` ни на что не влияет.

### 10.4 Тесты и CI

- **CI проверяет не тот интерфейс.** `pnpm test:e2e` в CI идёт по скрытому classic-пути,
  smoke-проверки читают исходники classic. E2E основного интерфейса запускается только
  вручную. → Перевести E2E и smoke на основной интерфейс.
- E2E есть только для Windows; Linux-job не собирает оркестрацию и desktop.
  → Сборка всего на Linux, затем tauri-driver/WebDriver для Linux.
- Компоненты тестируются через SSR и регулярные выражения по исходному тексту: такие
  тесты ломаются от любого рефакторинга и мешают переделке UI. → Playwright против
  UI Lab (mock host) и компонентные тесты с взаимодействием.

### 10.5 Поддерживаемость

- **Гигантские файлы:** `piui-index/src/lib.rs` — 338 КБ (там же даже настройки
  внешнего вида UI), `real_rpc.rs` — 191 КБ (путь classic), `api.rs` — 154 КБ,
  `workspace_api.rs`, `orchestration_api.rs`, `orchestration_scheduler.rs` — по 95–115 КБ.
  Строки во фронтенде доходят до 3000 символов (в `SystemGraphEditor.svelte` средняя
  строка — 133 символа). → Prettier/ESLint, разрезка на модули без изменения поведения.
- **Svelte 5 в legacy-режиме:** ноль runes, смесь синтаксисов, логика зависит от порядка
  `$:`. → Новые компоненты пишем только на runes, старые мигрируем при переносе.
- **Состояние:** в `WorkspaceShell` 71 переменная, в `App` — 90, самописная конкурентность
  внутри разметки. → Доменные сторы (чаты, запуски, каталоги, настройки), как и требует
  `AGENTS.md`.
- **Host API:** три системы ошибок, три проверки «это Tauri?», ручное зеркало типов,
  прямые `listen` из компонентов, шесть невызываемых команд. → Генерация TS-типов
  из Rust (specta/ts-rs), единая модель ошибок и подписок.
- **Контракты:** 23 версионированных файла, часть не используется вовсе (orchestration-host
  v2–v5, harness-models v14 и др.). → Правило: один живой протокол плюс мигратор
  сохранённых данных.
- **Classic переплетён с новым путём:** каталог workspace читает проекты из classic
  `ProjectIndex`, три модуля импортируют `api::verified_project_directory`. → Удалять
  classic поэтапно: сначала выделить общие сервисы.
- **Локализация:** два словаря с конфликтующими ключами (7 расхождений), 14 ключей
  с хвостовыми пробелами, нет правил множественного числа, даты по локали ОС,
  `locale-audit` не в CI. → Каталог ключей, ICU-плюралы, аудит в CI.
- **Диагностика:** stderr харнесов выбрасывается, ошибки сводятся к 13 кодам и дальше
  к `RUNTIME_FAILED`. → Локальный журнал диагностики с вырезанием секретов и понятные
  сообщения об ошибках.
- **Документация:** ≈ 840 КБ, заметная часть устарела (README, `contracts/README.md`,
  `CONTRACT.md`, `SYSTEM_FILES.md`). → Новые PRODUCT/ARCHITECTURE/README, мастер-спека
  и старые документы — в архив.

### Ф0. Стабилизация — M–L
Цель: надёжная и читаемая база, на которой можно быстро переделывать UI.
1. Проверить и закоммитить текущие UX-правки (20 изменённых и 6 новых файлов; check —
   0 ошибок, unit — 226/226). Нормализовать переводы строк через `.gitattributes`.
2. CI: E2E и smoke — по основному интерфейсу; Linux-job собирает всё; Prettier и ESLint
   (однократное форматирование отдельным коммитом с `.git-blame-ignore-revs`).
3. Зависания (§10.1): гейт, канал событий, таймауты, fsync, минимальная починка стора
   оркестрации, продолжение ручных запусков.
4. Производительность ленты (§10.2): батчинг, инкрементальный Markdown, пейджинг,
   виртуализация.
5. Дефекты адаптеров (§10.3), динамические слеш-команды Pi.
6. Диагностика: журнал, stderr харнесов без секретов, человеческие ошибки.
7. Перенести из classic то, что есть только там (диалоги и переключатели расширений,
   палитра, дерево сессии), выделить общие сервисы из `api.rs` и удалить classic,
   мёртвые команды, контракты и компоненты.

## 12. Что поменять в правилах проекта

`AGENTS.md` и ADR описывают «минимальную оболочку над Pi». Агенты, которые будут делать
эту работу, читают `AGENTS.md` и упрутся в устаревшие запреты. Предлагаемые ADR:

| ADR | Решение |
|---|---|
| ADR-026 Продукт | PiUI — рабочая среда для агентов-харнесов и конструктор мультиагентных пайплайнов, а не только оболочка Pi |
| ADR-027 UI-стек | Svelte 5 runes, bits-ui (headless), Lucide, Svelte Flow + ELK; без Tailwind (ADR-014 в силе) |
| ADR-028 Реестр харнесов | Открытый `HarnessId`, дескрипторы, диапазоны версий вместо пинов, Transcript Blocks v2, ACP как универсальный транспорт |
| ADR-029 Пайплайны v5 | Первичный документ пайплайна, каталог нод, выражения без eval, циклы с лимитами, Map, версии черновик/опубликованная |
| ADR-030 Хранилище оркестрации | Транзакционное SQLite-хранилище вместо перезаписи JSON на каждый переход |
| ADR-031 Плагины | Backend вне WebView под контейнментом, UI в sandboxed iframe, явное доверие, safe mode |
| ADR-032 Рабочие инструменты | Панель ревью диффа и worktree — в ядре; терминал, файлы, превью — первые официальные плагины (пересмотр ADR-015) |
| ADR-033 Скрипт-ноды | Код пользователя выполняется только при явном доверии к пайплайну; импорт никогда не запускает код |

Остаются без изменений: нативная история — источник правды; никаких своих провайдер-
клиентов и агентных циклов; никаких общих shell/fs API в WebView; доверие проектам;
safe mode; generic fallback; честное «это не песочница».

## 13. Решения

**Приняты 26.09.2026** (владелец передал право решать): гибрид; backend-плагины вне
WebView с явным доверием; Claude Code — через ACP, затем Agent SDK, **только по подписке**
(§8.4); скрипт-ноды — доверенный код Node/TS, shell, Python; графит + винный акцент,
системный шрифт, «Chaos energy» — опция; фоновый режим в трее — опция с явным согласием;
сначала Windows, Linux держим собираемым; строгий процесс для ядра, UI Lab для интерфейса;
название PiUI остаётся. Исходные вопросы оставлены ниже для истории.

1. **Стратегия:** гибрид «ядро сохраняем, UI пересобираем» (рекомендую) или полный rewrite?
2. **Плагины со своим кодом:** разрешаем backend-плагины (отдельный процесс, явное доверие)?
3. **Claude Code:** начинаем с ACP или сразу с Agent SDK? Нужна подписка или достаточно
   API-ключа (§8.4)?
4. **Скрипт-ноды:** какие рантаймы нужны — Node/TS, Python, shell? Принимаем, что это
   доверенный код, а не песочница?
5. **Визуальный стиль:** оставляем графит и винный акцент? «Chaos energy» — опция или
   убрать? Системный шрифт или Inter?
6. **Фоновый режим:** запускать автоматизации из трея и стартовать вместе с Windows?
7. **Платформы:** сейчас только Windows, Linux и macOS позже?
8. **Процесс:** строгий доказательный стиль оставляем для ядра, а UI-итерации облегчаем
   (UI Lab + скриншот-тесты)?
9. **Название:** оставляем PiUI, раз продукт уже не только про Pi?

## 14. Риски

| Риск | Что делаем |
|---|---|
| Переделка UI затянется и сломает рабочие сценарии | Новая оболочка собирается по экранам в UI Lab; старое удаляется только после паритета; E2E на каждом шаге |
| Нативные харнесы часто меняют протоколы | Диапазоны версий, проверка capabilities при старте, контрактные тесты на фикстурах, деградация вместо отказа |
| Условия использования подписок в сторонних GUI (особенно Claude) | Проверить до релиза; запускаем установленный пользователем CLI с его собственным входом и не трогаем учётные данные |
| Плагины как вектор атаки | Вне WebView, контейнмент, явные права, safe mode, отзыв прав при смене отпечатка |
| Скрипт-ноды выполняют код | Явное доверие к пайплайну; импорт не выполняет код; права видны; таймауты |
| Стоимость мультиагентных запусков | Лимиты экземпляров, итераций и бюджета как явные настройки; видимый расход; пауза при превышении |
| Разрастание модели нод | Строгий каталог, линтер «осмысленных нод»; новые типы нод — сначала плагином |
| Производительность WebView на больших графах и сессиях | Виртуализация, `onlyRenderVisibleElements` в Svelte Flow, перф-бюджеты в CI |

## 15. Конкуренты и чем PiUI отличается

- **opcode (бывший Claudia):** Tauri, только Claude Code — агенты, аналитика, MCP,
  чекпоинты.
- **Conductor, Crystal/Nimbalyst, Emdash:** параллельные агенты в изолированных
  worktree, ревью и слияние.
- **Zed Agent Panel:** параллельные треды, ревью по ханкам, внешние агенты через ACP-реестр.
- **Agor:** доска, где ветки — карточки; учёт стоимости; MCP-endpoint, через который
  агенты создают и форкают работу. Ближе всех к конструктору графов.
- **AionUi:** десктоп для 20+ CLI-агентов.
- **Sculptor:** Claude Code и Pi в изолированных окружениях.
- **OpenCode desktop, DeepSeek Harness web UI:** оболочки одного харнеса.

**Ниша PiUI** — сочетание, которого нет ни у кого из них: нативные харнесы (а не API),
смешанные по харнесам графы с долговечной оркестрацией и восстановлением, чат уровня
Codex и плагин-платформа. Это и есть продуктовая ставка плана.
