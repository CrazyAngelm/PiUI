# ADR-059 — Graph kernel v2: the portable document compiler boundary

Status: Compiler accepted in Stage 0, 2026-11-15. The Stage 5A extension below is accepted with its reviewed milestone commit.

A system graph is written once, as a portable system document
(`piui-system`), and runs on different hosts: Desktop's native host and the
server. This record fixes the first shared piece of graph kernel v2: one pure
Rust compiler from a version 5 document to the orchestration v6 run
definition. It fixes the compile input, output and refusals, and nothing else.
The contract is `contracts/nano-graph-kernel-v2.ts`. The compiler is
`crates/piui-orchestration/src/compile.rs` with
`crates/piui-orchestration/src/compile_tests.rs`. The equality vectors are
`contracts/fixtures/unified-shell/graph/compile-vectors-v1.json`, generated by
`apps/desktop/src/features/orchestration/compileVectors.ts`. Server paths
below are relative to the NanoAgentProject repository at `c20e7721`.

## Context

Today the same document is turned into a run definition in two places, and
neither is the kernel.

- **Desktop editor (TypeScript).** `parseSystemFile`
  (`apps/desktop/src/features/orchestration/systemFile.ts`) validates versions
  1–5 with the published schemas. It then checks structure, adapter settings
  (`src/harness-adapters/validation.ts`), `graphIssues` and sub-pipeline
  mappings (`src/host-api/subpipelines.ts`). `systemFileToGraph` gives the
  graph, team, pipeline and every profile a random UUID. `compileGraph`
  (`agentGraph.ts`) returns `{profiles, team, pipeline, command}`. On save,
  the host (`orchestration_save_graph_v6`,
  `apps/desktop/src-tauri/src/orchestration_api.rs`) runs
  `validate_graph_request`: `validate_definition` and `authorize_spawn` on
  that snapshot, with the command as `launchCommand`. `apply_graph_in` then
  checks revisions, `valid_for_workspace`, `check_saved_pipeline` and
  `check_parents` against the workspace. A run starts from
  `{teamId, pipelineId, launchCommandId}`. `create_run_in` snapshots every
  profile of the workspace, not only the graph's members.
- **Server (C#).** `HermesGraphDocumentValidator.Validate` checks the version 5
  schema when a draft is saved (`Services/Hermes/Graphs/`). At start,
  `HermesGraphAdmission.Compile(document, draftId)` maps the document with
  `JsonNode`:
  - It refuses team inheritance and any edge kind other than result and
    route, with `unsupported_cloud_delegation`.
  - It refuses executors other than `agent`, with `unsupported_cloud_executor`.
  - It refuses callable roles, with `unsupported_cloud_delegation`.
  - It refuses profiles that are not Hermes, native and a Nano mode, with
    `unsupported_cloud_profile`.
  - The profile id is the agent id. Team id and pipeline id are the draft id.
    There is no launch command.

  `HermesGraphExecutionService.StartAsync` sends the result to kernel
  protocol 1 `create` with native-only capabilities.
- **Kernel protocol 1** (`crates/piui-graph-kernel`) receives a definition, not
  a document. It refuses host-executed steps, team messaging, spawn grants,
  callable roles and allowed orchestration tools (`supported_definition`), then
  runs `validate_profile_capabilities` and `Coordinator::new_started_run`.

Stage 5A requires equality vectors that converge for three compilers. No Rust
compiler of the document existed to anchor them.

## Decision

1. **One pure function.**
   `piui_orchestration::compile_system_document(text, identity, pipelines)`
   returns `RunDefinitionSnapshot` or `CompileError`. Its refusal codes are
   `CompileRefusal`. It reads no file, clock, environment or random source,
   starts nothing and grants nothing. A compiled definition is a draft until a
   host freezes it in a run after its own admission.
2. **The host chooses every identifier.** `CompileIdentity` is
   `{teamId, pipelineId, launchCommandId?}`.
   - Each agent's profile id and member id is the agent's id, as on the server.
     The editor's random profile ids carry no meaning; the vectors rename them
     to agent ids.
   - With `launchCommandId`, the definition carries the launch command
     `{id, name: document name, teamId, pipelineId}`, as the Desktop save path
     validates it. That command id is the `launchCommandId` a Desktop run
     starts from.
   - Without it there is no launch command, as in server drafts.
   - `pipelines` (`{id, name}`) are the saved launch commands that a
     sub-pipeline step's name resolves against. An exact name wins; otherwise
     a unique case-insensitive match is used. A missing or ambiguous name is
     refused, and so is a step that runs the launch command being compiled.
3. **Version 5 only.** The editor remains the single importer of versions 1–4
   and upgrades them (`serializeSystemFile(systemFileToGraph(parseSystemFile(text)))`).
   The generator checks that the upgrade keeps the editor's definition. The
   Rust tests check that every shipped original of version 1–4 is refused as
   `unsupportedVersion`.
4. **Nothing is dropped or replaced silently.** Each of these is refused:
   - members that are unknown, `null`, missing or of the wrong type;
   - schema patterns and ranges, using JavaScript's `\s` set;
   - a member name repeated in any object;
   - nesting deeper than `serde_json`'s recursion limit (kernel v1 has the same
     limit).

   Numbers are read as `JSON.parse` reads them: `30.0` is the integer 30, and
   every carried number is its IEEE double. Where the editor replaces or drops,
   the compiler refuses with `invalidStructure`: a program router named as the
   orchestrator, or send, observe or spawn connections that touch a program
   router or host work. Positions and the placeholder profile of a step without
   a team member (except its name) are the only unmapped members
   (`PRESENTATION_ONLY_FIELDS`).
5. **Editor graph rules.** The result passes `validate_definition` and, for
   every grant, `authorize_spawn`, the checks the Desktop host runs on save. It
   also passes the editor rules that `validate_definition` states more loosely
   (`check_editor_rules`):
   - conditions and input bindings read declared fields of result
     dependencies;
   - review ancestry follows result connections beyond the direct
     dependencies;
   - an output field is declared by its step;
   - a sub-pipeline step source reads a declared field;
   - program router predicates use the fields their input declares;
   - declared result fields are unique.
6. **Not in the compiler.** These stay host-owned:
   - adapter settings checks, which are capability admission of the location
     that runs a step (the native host refuses unsupported settings before
     launch);
   - workspace checks and revisions of the save;
   - the run snapshot's profiles;
   - run inputs.
7. **Protocol 1 is unchanged.** Stage 0 defined no protocol 2 command, location
   binding or admission matrix; the Stage 5A extension below adds them.

## Differences from the server

Each vector's `server` outcome was derived from the server source. On
2026-11-15 root ran these outcomes in the server worktree with test code only
(`NanoAgentProject.Tests/Services/Hermes/HermesGraphCompilerParityTests.cs`);
product code was unchanged. The final fixture includes `llm-collaboration`
and the review regression `cloud-large-integer-serialization`.

50 C# tests passed: one per vector (49) plus a test of number spelling. For each
vector the test:

- runs `HermesGraphDocumentValidator.Validate` and
  `HermesGraphAdmission.Compile`;
- asserts the refusal code, the observed exception, or the predicted definition
  (`JsonNode.DeepEquals`);
- recomputes `differencesFromRust`.

The log is in the task scratch directory:
`stage0/server/compiler-parity-remediated49.log`.

Review found that casting an integral IEEE double to a Rust integer does not
reproduce `JSON.stringify`: `1000000000000000128` becomes
`1000000000000000100` in JavaScript. The compiler now formats finite numbers
through the ECMAScript-compatible `ryu-js` serializer before constructing the
JSON number. The real editor corpus covers positive/negative values in a router
predicate and condition; the focused Rust test also covers a plugin config.
The previous implementation failed that regression, then all 113 orchestration
tests passed with the correction. No provider or kernel process is involved.

No kernel process was started. The protocol 1 `create` outcomes therefore stay
predictions. `compile_tests.rs` checks them: each server definition must decode
with the kernel's types and give the predicted outcome under the protocol 1
support checks, `validate_profile_capabilities` and `validate_definition`.

- **Typed equality holds** under the server identity for `cloud-server-proof`,
  `cloud-routed-review` and `cloud-structured-review-inputs`. (Executed.)
- **Dependency order.** The server lists dependencies in connection order. The
  editor and the compiler list result sources first, then route sources
  (`cloud-dependency-order`). (Executed.)
- **Default orchestrator.** The server takes the first member, which may be an
  agent router. The editor and the compiler take the first agent that is not a
  router or host work (`cloud-agent-router-first`). (Executed.)
- **Number spelling.** `Compile` keeps `2.0`, `1.0`, `1.50` and `3.0` as
  written. (Executed.) The consequences are predicted:
  - `serde_json` reads `2.0` and `1.0` as floats, which do not equal integer
    results (`cloud-number-spelling`).
  - A review limit of `3.0` does not decode, so the server reports
    `kernel_invalid_response` (`cloud-integer-spelling`).
- **The server would run graphs that Desktop refuses.** The editor and the
  compiler refuse these six documents. The server accepts them (executed), and
  kernel v1 would create runs for them (predicted, checked in Rust), because
  `validate_definition` alone does not refuse them:
  - `rule-condition-through-route`
  - `rule-binding-through-route`
  - `rule-review-through-route`
  - `rule-output-field-undeclared`
  - `rule-predicate-on-added-field`
  - `rule-duplicate-declared-field`
- **Whitespace.** The draft validator and `Compile` accept a name that is only
  U+FEFF (`name-byte-order-mark`) or only U+0085 (`name-next-line`). (Executed.)
  The editor and the compiler refuse U+FEFF. For U+0085, the Desktop host save
  and the kernel's `validate_definition` refuse it (the kernel outcome is
  predicted).
- **Repeated names.** `Validate` accepts the document. `Compile` throws
  `System.ArgumentException` when `JsonObject` builds its dictionary
  (`GraphJson.Text`, `HermesGraphKernel.cs:90`, called from
  `HermesGraphAdmission.cs:73`). That is not a `HermesGraphRejectedException`,
  so the start fails without a refusal code (`duplicate-member-name`).
  (Executed.)
- **Deep nesting.** `Validate` and `Compile` accept it (executed). Kernel v1
  cannot decode the frame (predicted) (`nesting-beyond-parser-limit`).

## Stage 5A extraction boundary

- **Shared and pure (Rust):** the document compiler (this record). Stage 5A
  adds the agent-request admission module and protocol 2 next to it.
  Desktop's `orchestration_api.rs` and the scheduler change only their call
  points.
- **Host-owned, never in the kernel:**
  - native harness sessions and histories;
  - every effect: launch, cancel, scripts, plugin nodes, sub-pipeline
    children, approvals delivered to people, and files;
  - persistence and the outbox;
  - workspace checks and revisions;
  - proof of actual capabilities and current authority per location and adapter;
  - the list of pipelines that names resolve against;
  - run inputs from the request;
  - provider credentials.
- The editor keeps `compileGraph` until Stage 5A decides whether Desktop
  import and save call the compiler. The vectors then check both.

## Stage 5A extension

The compiler remains unchanged. Protocol 2 now wraps it and the existing
deterministic coordinator; Desktop delegates its agent-request admission to
the shared pure function with the same public error dispositions. A host opts
in using `--with-protocol-2`; default protocol 1 remains byte-compatible.

`validate` and `create` use the same pure definition refusal matrix over
host-proven capabilities and executor support. `create` freezes a location/
owner binding with the run. Subsequent commands recheck the stored binding,
definition admission and revisions, returning typed effects for atomic host
persistence. The host retains authentication, current authority checks,
history verification, runtime effects and the outbox. The private binding is
trusted persisted host data, not a MAC or a credential supplied by a browser.

Protocol 2 adds host executors, coordinator tool admission and nested-run
transitions without a second scheduler or model loop. Its explicit refusals
and differences from the native caller are recorded in
[KERNEL_V2_RESULT.md](../nano-unified-shell/KERNEL_V2_RESULT.md). Source and
Windows/Linux process artifacts are available; importing and proving the
binary in the pinned server image remains Stage 5B. The original Stage 0
evidence above remains historical and is not relabelled as process evidence.

## Remaining integration

- Each real host must prove which capabilities/executors it offers before
  binding the shared matrix; schema validity is not runtime support.
- The shared editor/import/save integration remains Stage 5C. Native Desktop
  does not yet adopt protocol 2's stricter preflight for unused authority.
- Sub-pipelines on the server: which launch commands a cloud name resolves
  against, and with which identity.
- Kernel rollout: the protocol 2 binary, its provenance manifest and the
  server's switch from protocol 1.
- Server changes for the differences above. Stage 0 leaves server product
  code unchanged. The open items:
  - the editor rules;
  - number tokens;
  - repeated names;
  - the default orchestrator;
  - dependency order;
  - whitespace.

  Each change, and the protocol 1 `create` outcomes, needs its own executed
  proof. The final C# fixture has run; protocol 1 process execution and the
  planned server behavior changes remain outside Stage 0.
