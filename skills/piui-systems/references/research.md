# Research and design synthesis — 2026-09-06

These are design inputs, not a claim that PiUI implements every source's features.

- In the supplied [250-agent video at 23:36](https://www.youtube.com/watch?v=gNsjZvzdGEE&t=1416s), the author separates when to invoke a type, desirable input, expected result and system prompt. At 24:26 onward he demonstrates dynamic task-taking/groups; those persistent group semantics are not PiUI v1. The comparison used the video's actual Russian caption transcript already extracted locally, not a newly invented transcript or access to the paid source.
- The [Kimi video around 08:05](https://www.youtube.com/watch?v=u3gbL1cEEUs&t=485s) describes adding coordination to developer/reviewer loops. PiUI configuration should state acceptance criteria and filter findings against the goal. It cannot promise a persistent evaluator loop by drawing a result cycle.
- [Anthropic's workflow patterns](https://www.anthropic.com/engineering/building-effective-agents) distinguish fixed workflows from dynamic agents; sequencing suits cumulative steps, parallel branches suit independent work, and orchestrator/workers suit decomposition discovered during execution. Apply the smallest appropriate pattern; additional agents have coordination costs. This 2024 article itself flags that tooling has evolved, so use it for the architectural distinction, not current product APIs.
- [OpenAI's orchestration guide](https://openai.github.io/openai-agents-js/guides/multi-agent/) distinguishes manager-owned agents-as-tools from transferring control through handoffs. In PiUI, workspace spawn/wait resembles manager delegation; a result edge transfers an artifact, not ownership of a persistent conversation.
- [JSON Schema object rules](https://json-schema.org/understanding-json-schema/reference/object) support rejecting unknown properties. PiUI uses that to catch misspellings or invented settings rather than silently dropping them. Semantic reference and permission checks remain separate from schema validation.

Our synthesis: **outcome → evidence → roles → dependencies → communication → authority → completion**. First define what proves the task complete. Then allocate only necessary work and independent checks; choose the harness by enforceable capabilities and available models; minimize the context passed across each result boundary. Review practical output quality and cost with an authorized representative run before increasing concurrency. There is no universal ideal agent count or reasoning tier.

Prompt structure is an operational checklist, not a security mechanism: invocation, input, responsibility, output, verification and completion/blocker. Rights and routing belong in configuration, and native enforcement must be truthful. If the user needs capabilities outside this format, identify the missing native/coordinator contract instead of encoding unsupported wishes in JSON.
